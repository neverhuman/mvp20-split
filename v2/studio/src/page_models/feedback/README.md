# Question and future-feedback lineage

Implemented boundary: `FeedbackContext` owns frozen question/need and explicitly selected assessment, publication, proposal and adjacent Research correction identities. `FeedbackLineage` relates owner records using exact references. `FeedbackModel` coordinates bounded reads with generation checks and cancellation, exposing a stable subscribed snapshot. Its dependencies are the public `ResearchRecordClient` and `FeedbackClient` interfaces; there is no service state, owner implementation import or mutation.

One context belongs to one project. Need criteria must belong to the selected question. Assessment decisions must address the selected need; supporting/contradicting receipt artifacts must occur in the assessment request. Publication is optional and explicit so an unpublished assessment is still useful. An explicitly selected publication must identify that assessment and subject. Its qualified outcome remains authoritative; the model does not reimplement Research's receipt policy. A sufficient synthetic assessment is never scientific establishment.

Graph feedback must contain an assertion operation that explicitly links this question and need. Accepted changes must match the selected proposal and accepted head. Structural acceptance remains separate from evidence sufficiency. The projection does not invent provenance by matching labels, specimen names or context artifacts. It exposes evidence artifact references; measurement linkage requires owner provenance and is not inferred here.

The question view can compare adjacent Research correction revisions only when the next source receipt is the selected Research publication. Transport separately validates both record hashes, scopes and correction semantics; the model verifies the pair's predecessor and historical notice. Knowledge correction records remain available through the shared reader, but are not passed off as Research assessment publications. Active campaign state is neither selected nor mutated by this model. Future adoption requires explicit subsequent Runtime admission.

One request generation loads an atomic bounded record bundle. Bind, hide, refresh and disposal cancel earlier work. Stale or uncancellable peer replies cannot repopulate a new context. Reentrant subscribers can clear a context before reads begin. A denied or inconsistent read clears protected lineage; pending/failed scientific records are still records, distinct from transport failure. The page never polls hidden views or grows an unbounded history.

Rebuild acceptance: `tests/page_models/feedback.test.ts` covers immutable selections, explicit links, unmet/pending needs, qualified corrections, structural acceptance, reentrant and out-of-order responses, access denial, hide/show and disposal. Transport tests own wire validation/fingerprint checks. Visible UI and actual-owner progression remain BP-06.06/B2.03c/d; this module alone does not prove either.
