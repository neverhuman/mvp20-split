# Live curation qualification

UI-01.08/P5. This dev-owned harness qualifies the installed production curation
worker using one declared synthetic scope. It does not implement Planning behavior,
grant scientific authority, edit model output or reset accounting. Existing P4
reservations count against the same four-slot/$1 original-hold ceiling; no second
scope, refunded slot, provider retry or model fallback is allowed.

`prepare.py` uses the isolated P4 infrastructure and public Data publication to
freeze new truthful live-provider configuration roots, reviewed policy and worker
settings. It reads no model credential and issues no provider/campaign request.
`allowance.py` runs only inside the independently installed Planning interpreter;
its read-only transaction invokes the canonical budget checker and reports bounded
original reservations from Planning's own tables. The controller sees metadata,
never private SQL or model keys. Source/module edits stop during qualification.

Before live issuance require the frozen declaration, verified original allowance,
exact configured scope and reviewed policy. The production worker owns capture,
current processing permission, issuance, reservations and compiler progression.
Credentials must remain in environment/DPAPI and never enter fixtures or logs.
Live-model and LAN/cutover acceptance remain separate ordered P5 units.

`run.py` retains each scenario command before public intake, starts isolated owner
processes, and selects only that original curation. `worker.py` runs inside the
independent Planning installation with its actual configured OpenAI provider. It
exports the frozen envelope before issuance, then immutable output and accounting;
it never repairs a model response. The supported scenario compares exact returned
graph bytes with the compiled draft and executes a state-carrying successor. The
missing-capability scenario reads the durable requests without claiming fulfillment.
Original P4 campaigns and receipts are checked before and after each scenario.
The child process has a bounded lifetime and drains with its owning Windows job.
Credential loading is confined to the explicit live run; imports and preparation
do not read keys. Failed original calls retain their reservation and evidence.

`diagnose.py` reports strict-JSON duplicates and JSON-mode schema errors from
original captures. Its lenient decode is diagnostic only and can never enter the
compiler. `browser.py` qualifies the actual retained failure records, exact receipt
replay, disabled execution, desktop/narrow accessibility and final original budget
holds. Neither helper enables a model provider or claims successful live curation.

`preview.py` produces an explicitly offline, incompatible input-format proposal:
digest-verified readable schema documents and an explicit output construction guide.
It preserves original packet/capture files and cannot be used by the frozen worker.
Activation requires an additive reviewed profile and separate live qualification;
the preview provides no evidence of improved model accuracy or measured token use.
