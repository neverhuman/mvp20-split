## Concrete gap

The browser can launch a saved draft, inspect its original Planning proposal and
read actual retained runtime model responses. It cannot submit a new campaign
curation request and follow its durable progress. Planning's existing HTTP intake
is specifically for Runtime supervision; it is not a campaign conversation API.
The compiler helper used for provenance qualification injects a deterministic
proposal. It must not become the browser's backend or masquerade as a live model.

Existing foundations can be reused: campaign context/slice preparation, exact
Registry/Knowledge/Research reads, durable provider issuance/accounting, immutable
capture, compiler save/validation and Runtime's graph.admit_draft_successor command.
Two remaining incompatibilities are explicit: the deployed packet-aware OpenAI
envelope accepts supervision only; Deployment LaunchSpecification accepts AdmitDraft
only. Neither can be relabelled as campaign curation or successor launch.

## Request, state and replay rules

The submitted command carries at most4096 characters of human direction, an exact
predecessor run and saved-draft revision/content digest, explicit Knowledge and
Research references, selected input artifacts and a configured curation-policy ID.
Scoped principal identity comes from authentication. Client-supplied provider URLs,
arbitrary prompt text, arbitrary schemas or spending-limit increases are rejected.
The text is user intent within reviewed instructions, never an authorization grant.

Planning records the immutable command before work. Exact retry recovers the
original receipt/job; the same identity with changed bytes conflicts. A separate
managed Planning worker leases one bounded job, assembles public owner context and
records omissions, performs current Data processing checks, freezes the actual
transmitted envelope, reserves cost, then uses the existing once-only issuance
mechanism. A transport interruption leaves an explicit pending/unknown outcome;
refresh never initiates another paid attempt. No SQL transaction spans model/peer I/O.

Read states distinguish queued, assembling, awaiting_provider, proposed, abstained,
compiling, ready, failed and indeterminate. Model refusal, invalid graph, missing
capability, denied source, expired eligibility and unsupported local deployment
are distinct reasons. A proposal or saved draft is not an admitted campaign.
Original histories remain readable after replacement and future-only corrections.

Use a new campaign-specific input-bound/envelope identity rather than changing
the supervision profile. Exact instructions, schema guidance, inventory, scientific
context and provider framing count toward the input allowance. Preserve original
provider bytes; an adapter must not substitute a hand-authored valid graph after
the model returns. Compiler review continues to enforce tool, graph and authority
bounds independently of the model's explanation.

## Inventory and missing capabilities

Use existing bounded Registry retrieval and exact release descriptors, recording
scan completeness, selected version/digest, ports, representation, applicability,
resource/effect constraints and omissions. Do not send all releases automatically
or treat an inventory match as scientific qualification or capacity reservation.

A missing-capability request has stable scope/identity, original curation/proposal
reference, purpose, expected typed inputs/outputs, scientific applicability,
evidence need, acceptance criteria and the graph gap it addresses. It survives
reload independently of whether an executable graph can be produced. Initial
status is requested. Fulfillment is an explicit authorized command that verifies
the selected Registry release and retained acceptance evidence; retain the original
request plus fulfillment event, never rewrite it. False/unavailable matches stay
unresolved. No package installation or tool-code generation occurs in this scope.

graph diff, missing capabilities and validation outcome before enabling an existing
