## Ordered Implementation Deliveries

### B1 - Implement the owned boundary

Build repeatable install/start/drain/stop commands with independently packaged services; create restricted identities and explicit service routing. Add bounded structured logs, metrics and correlation without dumping secrets/raw scientific inputs.

**Exit:** Versioned contract examples, owned schema/migration or transport mapping, valid/invalid fixtures and compatibility notes exist. ### B2 - Implement transitions and policy

Startup migrates only under dedicated owner credential, then starts restricted service roles; no startup reset. Dependency failure marks readiness unavailable and preserves durable work. Shutdown drains at declared boundaries; failed migrations require explicit forward repair.

**Exit:** Focused domain/policy tests assert the declared state changes and prohibited transitions. Persist authoritative decisions before exposing success. Backend commits and external effects remain separate; retries do not assume network exactly-once behavior.

### B3 - Prove failure and recovery behavior

Fresh target install reproduces hashes; wrong role/network scope denied. Kill dependency, fill bounded test storage and simulate unavailable provider; readiness/diagnostics show the true state without dropping accepted data. Test selected CPU/accelerator artifact compatibility.

**Exit:** Expected results are independently specified from the implementation. Use actual PostgreSQL, separate processes, browser or model wherever the stated behavior requires it. Record setup, barrier, interruption, observation and exact identities; fake peers prove only the client boundary.
