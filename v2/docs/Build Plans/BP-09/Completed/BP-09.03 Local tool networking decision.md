# Local Linux tool connectivity

Status: TLS connection profile selected for engineering qualification; not yet implemented.
Reviewed `2026-10-07 00:19:43` (America/Chicago). Owner: local Deployment.
BP-09.03/B1.3 dependency; no implementation credit.

The selected scientific releases are Linux x86_64 containers. Runtime/Data owner APIs
are Windows processes listening on 127.0.0.1, consistent with computer-only access.
The Tool Protocol SDK permits non-loopback connections only through HTTPS. Preserve
that guard, source service isolation and actual tool descriptor identities.

## Observed host behavior

Two actual temporary Linux containers used harmless sentinel listeners, not application
credentials or scientific data. Both containers were removed afterward.

- `--network host` to a temporary Windows 127.0.0.1 listener: connection refused.
- Default Docker network to `host.docker.internal` at a temporary Windows 127.0.0.1
  listener: sentinel response received. This proves routing only, not TLS or SDK eligibility.

Docker reports Desktop4.77.0. No global settings were changed. Host networking is an
opt-in Desktop feature whose activation requires apply/restart; see
[Docker host-network documentation](https://docs.docker.com/engine/network/drivers/host/).
A global restart would affect other containers and would need owner direction. The
working private route makes that change unnecessary for the selected engineering path.

## Required TLS boundary

Use a local Deployment-owned TLS proxy with fixed Runtime/Data upstream mappings,
Windows loopback listeners and explicitly trusted local certificates for the tool
containers. No unverified certificate bypass, global trust installation, arbitrary
upstream selection, LAN listener or SDK HTTP relaxation. Private key material must
follow the existing deployment credential/file protections. Container trust is scoped
and explicit; certificate replacement must not silently change pinned configurations.

Qualify certificate hostname/chain validation and rejection, bounded request/response
forwarding, original public owner authorization, process shutdown and container access.
Then qualify pinned scientific images through actual Runtime/Data APIs. The temporary
HTTP sentinel was only a route probe; it is not the production transport design.

TLS connectivity does not establish a network-egress sandbox, tool eligibility or
scientific correctness. Those claims remain separate gates. No Kubernetes or native
Windows relabeling is implied. B1.2 adapter/allowance verification precedes B1.3
implementation; no current owner decision blocks independent progress.
