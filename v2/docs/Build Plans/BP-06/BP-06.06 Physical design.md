## Ownership and route boundaries

Knowledge owns accepted scientific graph revisions and their bounded projections. Research owns material/sample/experiment/observation semantics and scientific comparison views. Data owns exact source/trace/Artifact bytes, current access, representations and retrieval. Runtime owns campaign admission, pinned receipt consumption and successor lineage. Studio composes authenticated public reads through separate same-origin adapters; it owns disposable selection/layout/loading state only. The integration harness is verification tooling with public contract dependencies, not a fifth business service or authoritative joined database.

Existing Runtime ViewCatalog and read cuts stay intact. Explore receives a separate capability/projection source for each scientific owner, each with version, query limits and exact source revision/context. Missing support is unavailable rather than an invented empty view. Owner descriptors cannot choose arbitrary browser routes or install scientific code.

## Bounded Knowledge projection

[Knowledge exploration contract](BP-06.06%20Knowledge%20exploration%20design.md) specifies exact history/alias semantics, query identity, continuation, byte limits and the additive release boundary.

Introduce focused Knowledge query/projection objects and additive public DTOs. Search is literal label/id text with explicit bounded length; neighborhood expansion uses one exact accepted DomainRevisionRef, an optional exact focus and bounded radius0..2. No arbitrary query language. Stable deterministic pages bind scope, revision, view version, complete filter and continuation position. Changing any pin requires a new query; a later graph head never silently changes an old page.

Return compact entities/assertion summaries with explicit returned/remaining scope and unresolved endpoints. Detailed assertion grounding is loaded on selection. Preserve posture, polarity, aliases/retractions and exact source links; projection cannot convert reported/hypothesized claims to scientific truth. Initial bounds: at most64 entity summaries and128 assertion summaries in a neighborhood response, with a1MiB transport ceiling; search pages at most50. Exact row and byte accounting must both hold; oversized detail fails explicitly rather than truncating scientific meaning. Owner may read its retained snapshot internally; Studio must not fetch a full4096/8192 graph merely to hide rows.

## Bounded Research projection

[Research view contract](BP-06.06%20Research%20views%20design.md) binds exact experiment/specimen and explicitly selected observation pages, with lossless series windows.

Material view pins exact candidate/material/sample revisions. Property view retains original decimal spelling, censor/missing/uncertainty, method/unit/applicability and measured/inferred context. Same nominal candidate does not merge different preparations; normalization is an explicit retained Research interpretation, never a browser convenience. Preserve equal-time observations and divergent replicates. Paginate with stable source/query context and visible incompleteness; exact available selectors come from Research's owned records, not a cross-service search join.

Existing exact material/experiment/observation/decision reads and correction/impact APIs remain compatible. Add source-owned capabilities/projections where absent. Artifact-backed model/interpretation evidence is inspectable provenance; no universal model-evidence score or real model registry is inferred.

## Explore consumer and provenance

[Studio scientific transport](BP-06.06%20Studio%20scientific%20transport%20design.md) specifies generated owner groups, exact query guards, transport bounds and source-span verification.

Primary user: internal researcher inspecting why a graph claim or laboratory result is used. Primary action: search/select a scientific object, expand a bounded neighborhood and follow its exact evidence. One growing graph/list region and selection inspector reuse existing Studio tokens, controls and request lanes; material/property tables occupy selected views, not stacked dashboards.

Use owner projection -> focused page model -> render props. Selection carries exact owner/scope/revision/query identity. Independent lanes expose loading, empty, partial, stale, denied, failed and ready states; out-of-order responses cannot overwrite a newer selection. Denial/context changes clear protected data. Hidden views stop work and become stale. No in-campaign scientific edit action.

Provenance path: claim/observation -> exact conversion/interpretation record -> Data source/Artifact -> selected byte span. Current Data access and byte/hash verification precede displaying source text; rendering treats source instructions as text. No automatic external links, snippets from unauthorized targets or opaque-ID copy/paste requirement. Browser verification includes keyboard paths, narrow layouts, long labels, partial links and source-denial recovery.

## Scenario and iteration protocol

The verification manifest is versioned, credential-free and bounded. Focused groups pin question/need/method, source/trace/span, accepted graph/assertion, material/sample/observation, representation profile/generation, named-view versions and Runtime campaign cuts/receipt Artifacts. Domain scenario objects own cross-scope/context checks and deterministic fingerprints; Pydantic/JSON forms serialize boundaries. Shape validation proves neither actual owner existence nor scientific acceptance.

An actual-peer scenario driver prepares data through reviewed public commands, captures returned immutable refs and rereads them through their owners before recording a completed checkpoint. Four-owner processes have separate credentials/state; scripts never query another owner's private tables. Fixture values independently specify expected outcomes; reference-source answers are not scientific truth.

Scenario1 admits a pinned campaign from accepted bounded evidence, traverses knowledge/lab/source views, and records explicit partial/unknown outcomes. Scenario2 corrects the source/result/knowledge chain while the first campaign retains its original pins, then explicitly admits a successor with corrected refs. Two specimens with the same nominal candidate and different preparation remain distinct. Runtime acceptance—not the UI, manifest or LLM—governs consumable evidence. Fixture feedback proposals have no automatic scientific authority.

## LAB-REF01 actual-owner acceptance

B3.01 consumes completed B2 exact specimen and graph pins. The public driver exercises one-row Knowledge entity, Research specimen and property windows; changing filters or observation order must reject a prior cursor, and foreign scope must fail at the owner. Repeating the original request preserves its immutable page despite the later corrected head.

The production Explore workspace runs in Chromium through a loopback acceptance adapter, with separate read-only owner principals injected server-side. Boot data contains only exact public pins. The adapter accepts the production read-route allowlist, rejects mutation routes/browser credentials, bounds request/response bytes and time, and never imports owner implementations. Keyboard selection reaches exact claim/source/trace; visible next controls traverse the actual pages. Foreign context clears old protected detail. Desktop/narrow accessibility, overflow, console and screenshots remain required. This harness is not a production authentication gateway; independent consumer replacement remains B3.04/V1.

## LAB-REF02 correction ordering

With B3.01 accepted, open an actual Runtime wait pinned to a Research correction-chain root. While consumption remains pending, release two public Knowledge correction proposals from one accepted base and two Research correction commands from one expected head through bounded client barriers. Each owner must persist one winner and report the competing conflict; the barrier controls request release, not an internal database scheduling point. Existing owner-local transaction-barrier tests remain separate evidence.

Read exact proposal/correction history and replay the winning command. Submit the actual notice and successor receipt to the old wait: both must be rejected without changing its expectation or closure. Then consume the original receipt, retain its output and replay after Runtime replacement. Explicitly admit a successor pinned to the winning revision and preserve different output/plan identities. These are synthetic accepted evidence profiles; no unaccepted proposal becomes a campaign input. The accepted Knowledge branch remains a future option, never automatic graph replacement. No performance or physical scientific validity claim follows.

## LAB-REF03 incompatible observations and omitted specimens

After B3.02, retain a synthetic raw observation that reports the first sample with the second prepared state, another method/unit and an explicit quality flag. Observation storage may retain untrusted claims; retention is not matching or scientific acceptance. Read the exact public property projection and compare through the production Studio model: conflicting sample/state leaves nominal-candidate association unresolved and preserves the original value, method/unit and flag. A purpose-specific Research assessment must independently mark the mismatched report unknown; existing valid decisions remain unchanged.

Compare the two valid actual observations against a one-row specimen window. The missing specimen must remain outside_window rather than being inferred from the shared nominal candidate. Follow the real next-page control and preserve the complementary unresolved association. In the browser, inconsistent evidence remains visible, with qualified context and no automatic unit conversion or reuse verdict. This uses Research-owned synthetic fixture installation, not physical lab intake.

## Independent reconstruction and replacement

B3.04 starts after the three LAB-REF gates. Stop the owned Data process while Knowledge rebuilds its current semantic snapshot from accepted history through the public rebuild API; no source reread or scientific reacceptance is implied. Compare exact historical/current snapshots and pinned pages. Restart Knowledge and Research as fresh processes using their independently installed packages and private retained stores.

Restart Data against the separately owned second Qdrant backend. Retained terminal results remain readable, but a new query against an absent physical projection must fail explicitly. Reconstruct a new, explicitly selected generation from the same retained binding/profile via the public generation API and expected old head; compare exact ranked bindings/scores. This is a new generation, not a same-ID rematerialization API. Neither backend volume is reset or deleted.

Stage Studio source/public schemas in an isolated temporary workspace, install its exact lock and run owned tests/type/schema checks. Run the compiled production readers and full actual-owner browser journey again from that independent installation after replacements. Credentials stay in controller/Node server memory. Preserve original owner records, scope denials and historical pins; package independence, process replacement, physical backend reconstruction and scientific validity remain distinct claims.
