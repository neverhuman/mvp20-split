# Feedback lineage implementation

Design status: bounded implementation design, 2026-10-03. Owner: Studio feedback projection and cross-owner acceptance harness. Parent: [feedback integration](Completed/BP-06.06%20Feedback%20integration%20and%20closeout.md).

B2.03 has four equal implementation substeps: a public committed-record reader; b focused lineage/context model; c visible qualified lineage and browser verification; d actual-owner successor progression. Each requires its own verification; no new delivery denominator or change in approved scope.

Research owns the question, predeclared need/method, measurement and purpose-specific assessment. Knowledge owns proposed graph changes and their structural dispositions. Data owns source/derived bytes and current access. Runtime owns campaign pins and receipt consumption. Studio reads those authorities; a locally assembled scene is neither a persisted feedback proposal nor an acceptance decision.

Use existing Research assessment/publication and explicit receipt-selection contracts, Knowledge proposal status and accepted-change records. An accepted Knowledge proposal already records source grounding, rationale, affected operations, disposition and successor graph identity. Preserve rejected and pending proposal records too. Do not invent a second generic proposal owner or present an uncommitted UI object as durable feedback. Any link to a measured result must follow an explicit owner reference; matching a label or context is not sufficient provenance.

The model must keep question/need/method, accepted scoped answer and evidence gaps separate. Synthetic sufficiency and logical entailment are not scientific establishment. A correction identifies a later revision and an improvement opportunity. Opening its history must not look up a mutable head or replace active campaign inputs. The historical and successor selections are explicit independent contexts; later campaign adoption is an explicit Runtime admission.

The visible view must retain unresolved needs and qualified outcomes, expose exact source/trace/receipt and proposal links, and describe future applicability. It must not add an in-campaign human approval gate or global quality veto. Rich prioritization and human/AI quality work queues remain SQ-01.

Actual progression must publish/commit owner records before displaying success, preserve old reads after replacement, and show independently specified differences between old and next pins. B3.02 adds actual race barriers and failure recovery; it does not substitute for B2.03's working end-to-end progression.
