# Draft successor admission correction

- Status: proposed; owner direction pending for material public execution-contract change.
- Reviewed: 2026-10-06 16:34:46 (America/Chicago).
- Owner: Runtime admission; Planning remains proposal-only.
- Active scope: BP-08.04/B2.02. B2.01 offline comparison proceeds independently.
- Implementation: 0%; existing contracts and admission behavior remain unchanged.

## Reproduced gap

The current public `AdmitDraft` rejects `predecessor` and `carried` as extra
fields. `SuccessorProposal` rejects `draft`. A direct validation probe against
the installed public contracts reproduced all three `extra_forbidden` errors.
Runtime `GraphAdmission.admit_draft` uses `DraftAdmissionGuard` but explicitly
sets successor false. `admit_successor` resolves only the configured plan
catalogue. Hosting deliberately reserves `PublishedPlanCatalog` for execution
of already-admitted plans; substituting it into admission would bypass the
current draft head, universe and Registry eligibility guards.

Consequently a newly compiled Planning topology proposal cannot currently be
admitted with atomic predecessor/carry lineage through the public API. The
activation audit correctly identified the reusable transfer machinery but
missed this composition gap. Manually adding each proposal to host configuration
would demonstrate preconfigured successors, not the autonomous proposed-draft
handoff required here.

## Recommended additive correction

Add public `AdmitDraftSuccessor`, combining the existing exact draft selection,
plan/input/budget/limits, predecessor cut and explicit carried mappings. Give it
a new command family `graph.admit_draft_successor` and route
`POST /v1/graph-runs/draft-successors`, installed only when draft admission is
configured. Preserve existing command families, canonical byte profiles,
schemas and original receipt replay unchanged. Publish additive schemas and
version the affected packages; freeze all predecessor schema hashes.

Use the existing Runtime admission transaction with both guards enabled:

1. Authenticate, register the original command and return terminal replay before
   consulting current configuration or peers.
2. Resolve the selected validation material and current Registry eligibility
   outside SQL, as existing draft admission does.
3. Under the admission guard, recheck exact current draft head/universe and
   freshness, then lock and verify the terminal/settled predecessor cut.
4. Resolve/hash/type-check carried inputs against the compiled plan; enforce
   existing budgets, expansion limits and one-active-run rule.
5. Commit the new run, draft admission, immutable successor lineage, audit/outbox
   and original command receipt together. Any failure rolls back the whole
   transition. Changed human inputs affect future campaigns only.

No implicit promotion of historical published plans, active-run mutation,
second scheduler, hidden human campaign gate, shared SQL ownership or scientific
authority is introduced. Schema changes do not authorize new paid model calls.
Existing tables appear sufficient; confirm during implementation before claiming
no migration is required. Retained comparison/proposal linkage remains Planning
responsibility and does not grant execution authority.

## Verification and ordering

After approval, keep B2 as two equal units and implement this correction within
B2.02, before actual topology compilation/admission evidence. Do not reopen
closed predecessor plans. New contract tests must reject missing/foreign pins,
duplicate carried targets and unsafe numeric values while preserving every old
schema hash and command replay fixture. Actual SQL tests must prove the combined
head/universe/eligibility and terminal/cut/value guards, concurrency, atomic
rollback and original accepted/rejected replay. Actual public-owner acceptance
must compile a proposed edit, carry compatible retained data, reject premature
adoption and reread immutable lineage after replacement. Existing draft and
configured-successor suites remain regression gates.

The alternative is to keep only manually configured successor plans for this
release and explicitly defer autonomous draft-successor adoption. That reduces
the currently intended B2 outcome and requires owner scope direction too.
