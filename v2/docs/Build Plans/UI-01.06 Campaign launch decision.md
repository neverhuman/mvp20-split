## Existing capability and observed gap

Studio DraftActivation already submits graph.admit_draft for an exact saved and
validated draft, and reconciles an ambiguous receipt. Runtime owns its conditional
commit and returned run ID. The demonstration currently bypasses browser authoring:
dev/run_scientific_demo.py compiles a prepared definition, admits it, then reconstructs
run-specific worker manifests and starts them through Deployment. That dev helper
is not a deployable UI launch boundary.

Deployment scientific_workers/profiles.py requires a nonempty run_id in each
immutable tool configuration. Its existing scientific-worker control commands
accept no payload; they operate prebound names only. The supervisor retains fixed
bindings, and pending old container journals cannot be omitted on replacement.
Gateway currently exposes neither Deployment peers nor supervisor control. Thus a
new Run button could admit a campaign but would not cause the scientific workers
to execute that run. Simply proxying control/start cannot fix the missing binding.

## Recommended boundary

Add a focused campaign_launch module under Deployment, with its own README,
domain objects, published Pydantic request/receipt schemas, journal, policy and
module-contained tests. Give it a narrow authenticated loopback API/credential,
separate from operator supervisor control. Gateway gains only this explicitly
configured peer. No generic command, executable path, image override, filesystem
path, secret, Docker option or process-control operation is accepted from Studio.

Deployment composes lifecycle; it does not validate science, compile graph internals,
write Runtime state, decide graph admission or fabricate execution status. Runtime,
Registry and Data remain independent public authorities. Do not create a shared
backend or move scientific tool implementations into the launcher.

Proposed public surface, version1:

| Operation | Meaning |
|---|---|
| POST /v1/campaign-launches | Persist/replay a bounded launch request and return its launch receipt; asynchronous admission/engagement follows |
| GET /v1/campaign-launches/{request_id} | Read the same scoped request and reconciled launch state, including actual Runtime receipt/run reference when known |
| GET /v1/campaign-launch-profiles | List eligible operator-installed profile references/capability constraints for this scope; no host paths or credentials |

Request contains wire_version, scoped actor/request identity, exact launch-profile
reference/hash and the existing complete graph.admit_draft command (exact draft,
validation/universe/plan pins, input artifact bindings, limits and budget). Profile
is an operator-installed policy and reviewed tool-image/resource/adapter allowlist,
not a hardcoded graph topology. The first installation may support only the two
existing scientific tool adapters; unsupported tool contracts return explicit
capability_unavailable. Registry eligibility and current capacity still govern.

The client persists the request identity before submitting and reuses it for receipt
reconciliation after refresh/disconnect. Same identity+same canonical body replays;
same identity+different body conflicts. Duplicate clicks, lost replies and retries
must never produce another Runtime admission identity or silently select new inputs.
Read scope comes from authenticated grants, never from request IDs or URL authority.

## Lifecycle and recovery

1. Persist request/fingerprint under the installation's existing single-writer
   discipline. Reserve the single active launch slot; deny another active launch
   without cancelling or changing it. Check scoped profile, exact public draft/
   validation pins, input availability, Registry releases, resources and drained
   prior worker journals. Recheck relevant identities at their owning operation.
2. Persist admission intent and the exact Runtime command before any HTTP issue.
   Runtime performs existing graph.admit_draft guards. Unknown transport outcome
   remains admission_unresolved; reconcile the original command receipt. A404 is
   not proof of nonadmission. No new command ID, compiler probe or arbitrary retry.
3. After an accepted Runtime receipt, persist the exact run reference before
   constructing Deployment-owned bindings. Build only reviewed profile adapters,
   exact images, scope/run pins and bounded resources. Preserve existing worker
   intent/adoption/expiry semantics. A failure here reports admitted_not_engaged
   with the real run ID; it must not falsely report rejection or successful running.
4. Engage verified ready workers and native coordination/delivery. Expose separately
   request acceptance, Runtime admission, worker readiness and execution progress.
   Runtime observation APIs remain the source for node attempts/results/status.
5. On completion/cancellation, quiesce and reconcile workers before releasing the
   launch slot. Cancellation uses Runtime's existing command; it is not Docker kill.
   Restart adopts the same persisted launch and pending containers. An orphaned or
   ambiguous worker journal blocks reuse until reconciled; no journal erasure.

Proposed receipt phases: preparing, admission_unresolved, rejected,
admitted_not_engaged, engaging, engaged, draining, released, recovery_required.
Receipt carries safe reason codes, timestamps, exact request/profile fingerprint,
Runtime receipt/run reference and worker-readiness summary. Released describes
Deployment quiescence, not scientific success. Never infer campaign status from
process exit, or silently admit a replacement after launch failure.

## Studio workflow

Show Run only for an exact validated draft and supported profile/input bindings.
Separate original retained campaign inspection from a proposed next run; the existing
demo plan is not automatically a saved Runtime draft. Prepare a real draft through
public authoring/validation APIs during integration, preserving its retained Knowledge
context. Do not use test compiler probes for browser launch.

Run submits once, shows preparation/admission/readiness, then selects the returned
run in the same authorized project. Existing historical campaign remains reachable.
Persist unresolved launch identity locally and reconcile through the owner after
reload; browser state alone never says admitted. Do not silently fall back to the
old completed run. Bounded Runtime observation reads refresh live node states, parallel
work, retries, failures and outputs; hidden views cancel/pause their reads. Result
discovery must handle a running campaign before its finish context exists, using the
exact launch/draft association rather than claiming outputs already retained.

Human edits remain between campaigns. This introduces no intervention/approval
pause inside an autonomous run. LLM graph curation remains I1 and follows its gates.

## Alternatives and decision basis

Exposing operator supervisor controls would still lack dynamic run binding and would
grant unnecessary authority. Starting a dev subprocess from Gateway would give it
execution/lifecycle responsibilities and leave ambiguous admission/recovery undefined.
Broadening workers to claim arbitrary runs would change eligibility and could consume
unrelated retained work. These do not satisfy this bounded launch requirement.

The recommendation is additive but material: new public launch operations, a durable
cross-owner workflow and dynamic reviewed worker bindings. v2/AGENTS.md Canonical
Execution Rules require owner direction for "Material scope/sequence changes";
this is why implementation of this new boundary awaits the explicit decision.
