# Campaign result discovery decision

- Status: proposed; owner direction required before adding a public Runtime read contract.
- Reviewed: 2026-10-07 18:02:00 (America/Chicago).
- Owner: UI-01/N2; Runtime owns execution acceptance, Data owns artifact access,
  Studio owns bounded result presentation. No implementation credit for this proposal.
- Decision: add campaign-level discovery of retained result references, with a
  narrowly typed numerical-search presentation as the first consumer.

## Problem and evidence

The retained demo has completed numerical evolution, but Studio can currently
reach its outputs only by selecting individual activations and output ports.
`studio/src/transport/observations.ts` exposes node detail/output pages and
`page_models/evidence.ts` verifies those references. `EvidencePane` displays
scalar members and artifact metadata; it does not download checkpoint contents.

Research's specimen/property comparison requires exact experiment and observation
pins. Those records are a different contract from the demo's numerical search
checkpoints. The demo link has a question and domain graph, with no experiment.
Lab observations cannot stand in for genetic-search candidate fitness.

The published `contracts/search` already defines SearchSpec, SearchCheckpoint and
EvaluationObservation with candidate ancestry, generation, objective direction,
units, evaluation provenance and unknown outcomes. Data already supports protected
artifact content reads. Neither fact supplies a campaign-wide result discovery
page. This is a discovery/composition gap, not a missing optimization algorithm.

## Recommended additive boundary

Add a versioned, read-only Runtime result-reference page under its existing graph
observation API. Freeze the exact route/schema through a schema-first child task
after approval; proposed shape is a campaign `results` resource accepting the
existing snapshot token, an opaque cursor and a bounded page limit.

Each row identifies the exact read cut, activation/occurrence, output port and
member position, and retained value/artifact reference. Return total/omitted and
next-page state. Include only outputs accepted by Runtime at that cut; retries,
uncommitted tool responses and later revisions cannot silently enter the page.
Existing node/output routes and receipt/command bytes remain unchanged.

Runtime must not interpret molecule structures, fitness, units, confidence or
scientific validity. It indexes accepted execution references only. It does not
read Data's tables or introduce a shared database model.

Studio then resolves explicitly recognized search-schema references through Data's
existing protected content route, verifies size/hash/media/schema, and constructs
a bounded numerical-search projection. Unknown schemas remain inspectable metadata.
No schema selection by filename, node label or guessed JSON fields. Initial bounds:
one selected checkpoint plus one explicitly selected comparison checkpoint; respect
the public 256-candidate bound and a declared byte ceiling. Never traverse an
unbounded predecessor chain or fetch all campaign artifacts automatically.

Comparison requires the same pinned search specification and explicit generation
identity. Show objective direction/units, constraints, unknown evaluations and
declared synthetic/predicted/measured provenance. Different specifications appear
as separate contexts, without an improvement score. This is not a general molecule
renderer and does not establish scientific acceptance.

## Alternatives and tradeoff

1. **Recommended:** authoritative paged result discovery plus the first typed
   search consumer. Adds a small public Runtime boundary and consumer work, but
   gives future tool types a common route into a result-first workspace.
2. **Narrower consumer-only option:** traverse existing activation/output pages
   with an explicit scan ceiling and show incomplete discovery. Avoids a new API
   now, but increases browser requests and makes completeness dependent on the
   client's scan. It is feasible; the new API is an architectural choice.

Do not add a universal scientific result DTO or executable UI plugins in this
change. Rich tool-specific renderers/descriptors remain separately bounded work.

## Implementation and acceptance sequence if approved

1. Public schema and Runtime read projection: exact-cut pagination, scope/access,
   terminal/canonical outputs, cursor expiry and unchanged historical reads.
2. Studio owned transport/domain/presentation modules: bounded integrity-checked
   checkpoint reads, cancellation/denial clearing, unsupported-schema fallback.
3. Actual retained campaign: results discoverable without knowing a node name;
   compare two real generations, trace selected evidence, preserve unknowns and
   unchanged history. Independent consumer install and scoped drift audit.

Fold this work into N2 with an explicit revised task denominator before starting.
N3 and V1 remain downstream; no closed plan is reopened. Until this decision,
the UI must say when only domain evidence or per-step execution outputs are available.

## Why owner direction is requested

`v2/AGENTS.md` states: "Material scope/sequence changes need owner direction;
routine blocking repairs do not need unnecessary permission requests."
This proposal expands a Studio overhaul into a new public Runtime observation
contract. The existing UI repairs and navigation work are already authorized and
implemented; they do not wait on this decision.
