## Configuration and preparation

The existing reviewed campaign instruction profile already requires the selected output schema, exact references and bounded permissions, preserves weak science and prohibits active human rebasing. Reuse its original bytes and CampaignPreparation packet/rights checks. Do not fork prompt semantics merely because a new materialization output profile exists.

Checkpoint creation currently pins scalar policy but does not pin a model/context recipe. Autonomous preparation must not select changed operator configuration during an admitted campaign. Add an explicit policy profile with a context-recipe digest; keep the existing policy profile readable and usable for its existing boundaries. A reviewed recipe pins objective, prompt, model/configuration, static context references, declared actions, call limits and Planning budget-policy reference. It excludes the policy Artifact and dynamic checkpoint declaration so policy -> recipe -> static references stays acyclic. Exact scoped recipe bytes are selected by digest, never a latest alias. Live provider/model/egress/spend remains unselected; deterministic fixture recipes can prove implementation.

Prepare exact policy and checkpoint-declaration Artifacts through Data's public publication/rights boundary before constructing the Planning request. Runtime owns checkpoint facts, not scientific truth; policy and selected facts enter the packet as data beneath the unchanged trusted instructions. The declaration identifies concrete occurrence, original/refreshed scalar seed, permitted fields, bounds and remaining original ceilings. Missing processing rights or context remain explicit failures. An Artifact reference without successful owner evidence is not a prepared context.

## Atomic bounded request reservation

Extract RequestJournal's existing transaction body for reuse under the owning run lock. The autonomous path verifies original slot/policy/recipe, current relevant footprint, concrete target, original deadline, request lineage and absence of a winner. Insert request/outbox and immutable reservation together. Exact replay returns original records without another reservation; partial writes roll back together.

Reserve the request's entire physical-attempt ceiling against both slot and campaign model-call ceilings. This is conservative potential-call accounting, separate from Planning's actual token/cost ledger. No automatic refund follows from timeout, uncertain dispatch, early model stop or unused attempts. Every repair consumes a new logical request and reservation under the same original deadline/ceilings; relevant refresh preserves decision identity. The existing RequestSeries retains original objective/prompt/policy/model and required context while allowing attributable declaration replacement. No active human reconfiguration or fabricated paid-call grant.

## Planning execution and owner exchange

Planning's supervision HTTP API records requests but does not issue models. Wire an explicit owner worker that validates admitted recipe/budget configuration, prepares and journals the original CampaignPreparation, then uses PlanningRunner's existing request, budget, issuance, capture and settlement boundaries. No Runtime-private imports or Runtime SQL. Immutable intake replay is not permission for a second call. Paid-call uncertainty keeps its existing conservative charge and late diagnostic behavior.

Runtime delivery uses the durable outbox/lease and exact receipt/readback client, outside SQL. Planning publishes captured bytes through Data and sends the original response profile; Runtime obtains authorized exact capture bytes, records the response and invokes WinnerStore. Invalid/stale output can trigger a bounded attributable repair; deadline, missing context/provider or exhausted original allowance select the pinned fallback with retained reason. Runtime alone releases execution. Successor graphs remain future drafts; retained evidence requests and weak science never become invented measurements.
