## Ownership and exact peer capabilities

Planning owns proposal derivation, scoped effect selection, immutable prepared request bytes, dependency status, bounded dispatch/reconciliation and attributable outcome history. Research owns declarations/sufficiency; Knowledge owns structural graph acceptance and its accepted log. Data owns processing permission and Artifact bytes. No peer tables, private peer imports, new endpoint DTOs or model-selected routes are needed for this boundary.

Research0.34 offers POST /v1/questions and /v1/evidence-needs with exact ResearchQuestion/EvidenceNeed DTOs, separately granted declaration actions, and exact POST /v1/questions/read or /v1/evidence-needs/read. Success acknowledges the exact record's presence, not original creation or scientific adequacy. Registration actor metadata is private; Planning must not infer original authorship from a successful response. Unknown records404, denied401/403, changed identity/head409, invalid422 and uncertain503 are distinct.

Knowledge0.18 offers POST /v1/graph-proposals, GET /v1/graphs/{graph_id}/proposals/{change_id}, and POST /v1/graph-changes/read. A completed POST returns GraphChangeDecision; status supplies the exact proposal, original actor, request digest and optional decision. Outcomes accepted/rejected/conflict are all HTTP200. An accepted decision must bind the exact accepted-change record, canonical content hash, actor, proposal, policy, position and resulting head. Structural-only authority never becomes scientific acceptance. Rejected/conflict decisions are immutable; a pending status is not rejection.

## Request and receipt values

Use a separate owner_handoff module. An effect selects original actor/scope, exact owned trace and interpretation publication, kind and candidate local ID, with configured owner identity. The stable slot excludes changing payload/configuration so alternate bytes conflict instead of creating an unnoticed second effect. Pure values validate public DTOs and canonical UTF-8 bytes; persistence later proves origin. Raw caller DTOs or acceptance flags are not trusted preparation.

Research request fingerprints use the complete canonical declaration bytes. Knowledge request digests use the owner's published canonical proposal convention (sorted keys, compact UTF-8, nonfinite values forbidden), which is distinct from numeric command-envelope profiles. Status must match actor, proposal bytes and digest. Accepted readback also verifies exact base position+1 and resulting snapshot/change identity; never read a latest head to rebase an active proposal.

## Preparation and dependencies

Resolve the owned task/observation/prior/finalized interpretation before preparing an effect. New preparation reads permitted source and interpretation contents and pinned owner contexts outside SQL, then uses existing validators. Persist immutable first request/provenance/context witnesses before dispatch. Later replay verifies those bytes and original owned facts without rerunning scientific interpretation.

Questions precede their locally dependent needs and answer publication. Existing selected questions require exact public record readback; a different revision or implicit latest record cannot satisfy the dependency. Dependent slots remain pending/unprepared when their selected question is unavailable. Independent graph/question/need/answer work remains eligible. Separate per-effect preparation avoids permanently freezing an unrelated owner lane because one peer is unavailable. Structural invalidity and transient context gaps remain distinct, with bounded findings; no global quality veto.

Result publication remains in result_publication. The handoff coordinator schedules candidate-answer publication only after its local question dependency is acknowledged. That acknowledgment does not add scientific authority to the answer Artifact. Existing diagnostic slots remain immutable; owner-handoff outcomes need their own retained observation rather than overwriting an earlier structural feedback Artifact.

## Durable state and rights

A forward Planning migration adds owner-private immutable selection/preparation/events and separate lease/fence/position control. Existing planning0001..0010 and trace/result bytes stay unchanged. Scoped foreign keys bind original trace and interpretation. Histories have SELECT/INSERT grants; only control columns update. Each database operation is short; no peer I/O under SQL. DB-clock fencing rejects expired or superseded writes.

Persist dispatch intent before each write. Reconciliation reads the original identity first: an exact existing Research record can acknowledge presence; Knowledge status can remain pending, reveal a decision, or require original-request resubmission. A denied/unavailable/malformed read must never trigger a blind write. On explicit absence, or an exact Knowledge pending intent, any permitted retry sends the original prepared bytes/configuration/identity. Lost replies remain uncertain until exact readback; identity/actor/content conflicts do not become acceptance or new IDs.

Research registration does not enforce source processing permission. Before a new POST, Planning must freshly review source and interpretation processing permission against the retained exact inputs, without changing prepared bytes or pinned context. Historical exact readback can resolve an already-existing outcome without source processing. Knowledge additionally performs its own current processing checks. This distinction preserves historical replay while preventing a delayed new declaration from bypassing withdrawn rights.

## Transport and execution bounds

Use a compiled owner/method/route catalog, explicit scoped credentials/configuration, loopback endpoints and strict public DTO parsing. No caller/model endpoint, redirect, proxy, Python handler selection or automatic network retry. Writes/request payloads cap256KiB; exact references cap4KiB; Research records cap256KiB, Knowledge status1MiB and accepted changes1MiB. Reject duplicate keys, nonfinite JSON, over-limit and ambiguous media; never copy peer error bodies into durable findings.

One invocation has a shared20-second read/write window and at most4 exchanges for an effect; connect/header/body parsing share the remaining deadline with socket shutdown against trickling peers. No process lease can authorize effects after its guard fails. A pending effect may be resumed by the caller with the same identity; no unbounded internal polling. Retain at most64 event transitions per effect; explicit exhaustion remains inspectable. The coordinator visits bounded candidate slots once per invocation and preserves earlier useful outcomes when another fails.

## Storage implementation constraints

b.iii.b will bind each immutable selection to original owned task/trace/observation/prior and finalized interpretation facts. A prepared payload stores exact request bytes and bounded input-observation witnesses, not reusable source permission or regenerated scientific conclusions. Shared origin-loading mechanics may be extracted within Planning if result-history behavior/error codes and existing tests remain unchanged. Peer state remains outside owner SQL.

Separate immutable histories from mutable DB-clock control. Events distinguish recorded dispatch intent, pending observation, blocked operational input, explicit request/identity rejection and exact acknowledged outcome. Only the receipt value factory can turn owner records into an acknowledged outcome. A timeout or malformed success cannot create rejection/absence. Check fence, expiry and expected position at the actual write; a late HTTP result never authorizes a stale local mutation.

In particular, changed graph head, unavailable selected owner records and withdrawn process rights must not provoke guessed context or automatic active-task rebasing. Independent useful effects continue; future campaigns may use the retained findings.

## Verified coordinator sequence

For each selected effect, register the owned origin and return an already-terminal local record without peer/preparation calls. Otherwise acquire a bounded lease, reload state, and prepare only that slot if necessary. Review source and interpretation contents outside SQL; obtain pinned Knowledge context only for graph preparation and exact question context only where needed. Store the derived first request through the journal. An unprepared slot retains its identity; an input gap returns an explicit bounded invocation result without inventing an owner receipt or freezing another slot.

Read the original owner identity before any new POST. An exact Research declaration acknowledges presence. Knowledge status binds the exact actor/request and may be pending, rejected, conflict or awaiting accepted-change readback. Fetch that exact accepted change before acknowledging structural acceptance. A terminal readback needs no new source processing. Denied, malformed or unavailable reads cannot justify submission.

Only explicit absence or an exact pending Knowledge intent makes the original request eligible for submission. Check remaining event capacity, freshly review processing rights for its source/interpretation ancestry, then record dispatch intent and fence immediately before sending. A lost reply leaves durable uncertainty for a later invocation; do not retry the write inside a failure handler. Research success is factory-bound to the full request. Knowledge POST decisions require original status/readback binding. The four-exchange window can cover read, submit, status and accepted-change readback; budget exhaustion remains pending.

At63 retained events, skip new writes and permit bounded original-identity readback for a terminal outcome. New blocked/nonterminal observations cannot consume the reserved final slot. Invocation results may report capacity/availability without changing already retained history. Explicit HTTP request rejection is an operational finding; it is not a fabricated typed Knowledge decision.

The campaign-level handoff pass enumerates bounded observed candidate slots once: up to32 questions,32 needs,32 answers and one graph effect, as permitted by the current public draft schema. Local questions precede their dependent needs/answers; exact external question selection remains mandatory. Duplicate or invalid candidates do not gain new identities. Failure in one effect returns a scoped result and does not prevent unrelated effects from being visited. ResultPublisher retains answer Artifact ownership, and the pass performs no model calls or campaign repinning.
