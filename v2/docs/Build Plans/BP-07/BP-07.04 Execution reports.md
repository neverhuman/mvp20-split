## Runtime consumption units

c.ii.3 has three equal units, initially0%: a exact report binding and read transport; b Runtime-owned immutable report/disposition storage and winner integration (two equal parts: report journal; disposition/winner integration); c preparation/repair/fallback bridge. a/b100%,c0%; current c preparation/repair/fallback bridge. Successful report entries identify the exact observation expected from the existing response/capture path. A report alone never supplies a capture or accepted effect. Validate original Runtime reference/request hash, Planning engagement/request hash, sequential bounded attempt identities and stop consistency before retaining peer data. Owner HTTP authentication is still required; a DTO with plausible hashes is not remote evidence.

Runtime may retain the original report after a winner or deadline as diagnostic history, but acceptance still runs through current WinnerStore checks. Unknown/missing readbacks stay unresolved; never infer no call from404. Report read errors do not authorize another physical attempt. Original call/reservation ceilings remain the upper bound of every new logical request.

Disposition/winner integration records one immutable repair or fallback intent per original request, attributable to the retained report and optional exact response. Pending report/capture has no terminal disposition. Model acceptance uses the same run-locked WinnerStore transaction; a committed winner always precedes subsequent report/configuration changes. A repair intent is not a model-call grant: the preparation bridge must reserve remaining original allowance atomically before creating its child request. Exhausted slot/campaign reservations select the pinned fallback. Pre-call configuration/context/budget failures and uncertain/unavailable exhausted providers select pinned fallback; invalid output and model-policy rejection can request bounded repair with retained reasons. Weak science alone is never a repair/fallback reason.

Acceptance also rejects superseded request ordinals and, when a completion report is already retained, requires its exact observation hash. This closes the direct winner path as well as the autonomous loop: late diagnostics from an older request or different primary/late observation cannot win after a successor request or terminal report. Existing committed winners still replay unchanged. SQL integrity errors and unexpected implementation failures must propagate rather than being mislabeled as model repair needs.

Planning must distinguish a request stopped before any model call from an actual issued attempt. Add a versioned `CheckpointExecutionReport` readback bound to the original Runtime request digest/reference and original Planning engagement/digest. It carries a closed stop reason and an ordered bounded tuple of actual settled attempt references, observation hashes and statuses. Zero attempts is valid for pre-call context, configuration, deadline or budget failure; it is never represented by a fabricated ProviderObservation or usage charge. The report does not authorize a repair, refund a reservation, accept a graph result or claim scientific quality.

An attempt observation hash covers its public record encoded as UTF-8 JSON with sorted keys, compact separators, ensure_ascii=False and allow_nan=False. It excludes capture bytes; the existing observation binds their exact hash/size/completeness. Completed observations and existing settlements remain the accounting authority. DTO validation checks shape only; the Planning projection verifies original authenticated intake, exact attempt identity/order, capture/observation integrity, maximum attempts and stop-reason consistency.

The next unit must persist one immutable report per original request under Planning's existing request lock. Finalization reloads all owned attempts/observations/settlements, refuses in-flight dispatch, and prevents future new issuance for that request under the same lock. Original tickets/history still replay; late results remain separate diagnostics. Do not expose a caller-supplied tuple as persistence evidence. A stopped request cannot resume merely because configuration later changes; a new attributable request is required and consumes the original campaign ceilings.

Expose the report through an authenticated bounded read endpoint for the original actor/scope; absence means unresolved, not success or zero attempts. Runtime must bind it to its original command/intake before storing it. Successful/proposed attempts still require the existing exact capture publication/response path. A report cannot replace a missing capture or force winner acceptance. Pending publication stays visible until recovery or original deadline fallback. Runtime owns the immutable winner and applies pinned fallback; malformed or stale output repairs stay within the original deadline and reserved allowances. Concurrency, issuance/finalization races and independent installed peer evidence remain required gates.
