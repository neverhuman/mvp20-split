# Checkpoint execution reports

Design status: c.ii.1 verified100%; c.ii.2 persistence active. Contract and pure owner projection implemented. [Autonomous loop](BP-07.04%20Autonomous%20loop.md) owns sequencing and percentages. No live-provider decision is needed for deterministic implementation.

Planning must distinguish a request stopped before any model call from an actual issued attempt. Add a versioned `CheckpointExecutionReport` readback bound to the original Runtime request digest/reference and original Planning engagement/digest. It carries a closed stop reason and an ordered bounded tuple of actual settled attempt references, observation hashes and statuses. Zero attempts is valid for pre-call context, configuration, deadline or budget failure; it is never represented by a fabricated ProviderObservation or usage charge. The report does not authorize a repair, refund a reservation, accept a graph result or claim scientific quality.

An attempt observation hash covers its public record encoded as UTF-8 JSON with sorted keys, compact separators, ensure_ascii=False and allow_nan=False. It excludes capture bytes; the existing observation binds their exact hash/size/completeness. Completed observations and existing settlements remain the accounting authority. DTO validation checks shape only; the Planning projection verifies original authenticated intake, exact attempt identity/order, capture/observation integrity, maximum attempts and stop-reason consistency.

The next unit must persist one immutable report per original request under Planning's existing request lock. Finalization reloads all owned attempts/observations/settlements, refuses in-flight dispatch, and prevents future new issuance for that request under the same lock. Original tickets/history still replay; late results remain separate diagnostics. Do not expose a caller-supplied tuple as persistence evidence. A stopped request cannot resume merely because configuration later changes; a new attributable request is required and consumes the original campaign ceilings.

Expose the report through an authenticated bounded read endpoint for the original actor/scope; absence means unresolved, not success or zero attempts. Runtime must bind it to its original command/intake before storing it. Successful/proposed attempts still require the existing exact capture publication/response path. A report cannot replace a missing capture or force winner acceptance. Pending publication stays visible until recovery or original deadline fallback. Runtime owns the immutable winner and applies pinned fallback; malformed or stale output repairs stay within the original deadline and reserved allowances. Concurrency, issuance/finalization races and independent installed peer evidence remain required gates.
