# Campaign compiler and eligibility handoff

- Design status: bounded B2.02 refinement; no implementation credit.
- Canonical owner: [BP-07.03](BP-07.03%20Campaign%20proposals%20and%20context.md).
- Prerequisite: B2.01 combined decision policy; Runtime authoring and Registry public contracts remain authoritative.

## Ordered units

B2.02 has four equal units: a exact command and readback values; b bounded Runtime and Registry transports; c fresh selected-input, eligibility and budget preparation; d independent installation and actual-owner compatibility. All start at 0%. B2.03 owns durable dispatch, fencing and reconciliation. This decomposition preserves the existing B2 milestone weights. Unit a introduces no network effects; b supplies internal transport primitives, not an unjournaled orchestration path.

## Runtime boundary

Only a reconstructed CampaignDecisionReview with next_step compile_future_draft can prepare an authoring request. Rebind the original preparation, observation, declaration and reviewed budget before deriving output. Fix configured Runtime owner and authenticated actor separately from model data. Derive a stable scoped draft identifier and command identity from the original proposal/attempt slot, with explicit conflict checks if payload changes. Save a new draft with expected_revision 0; never overwrite a human or unrelated draft head.

Use public SaveDraft and parse_authoring_command for definition.save, explicitly preserving amphora-command-v2 numeric encoding. Retain exact canonical envelope, identity and request SHA. The authored content digest is Runtime's published draft-content profile, distinct from the compiler plan hash; a command receipt alone does not establish that the expected definition was stored. Read back DraftRevision and compare scope, draft ID, revision, title and the complete original definition. Derive definition.validate from that exact accepted immutable revision/content pin; keep its v1 command encoding unchanged.

Every DraftCommandReceipt must match the original identity and request digest. Pending remains pending; rejected remains rejected. Accepted save requires draft_revision and accepted validation requires draft_validation. Exact readback binds the receipt's object/revision/content and validates all original request pins. DraftValidation.structurally_valid, plan_sha256, findings and pending_checks remain distinct from successful storage of a validation record. An accepted command may record an invalid graph. No save or validation result means admission, activation or scientific acceptance.

## Fresh eligibility and prerequisites

Resolve only selected exact Registry locks, with reviewed descriptor ports and the declaration's eligibility_context. Bind returned observations to scope, full lock, policy, lifecycle and all structural/scientific/capacity/admission statuses. Candidate observations expire; they are not worker reservations or execution grants. Synthetic-only current Registry policy stays explicit. Runtime repeats its own current admission checks later; Planning cannot transfer an eligibility observation into an execution right.

Before a new dependent handoff, re-read the policy-selected original identities through existing public owner readers. Verify current source processing permission independently of historical byte availability. Compare relevant Research/tool/input identities and selected Runtime locks without treating unrelated inventory or universe changes as blanket staleness. Changed relevant inputs produce a named stale proposal; preserve original bytes and do not repin an active campaign. Missing or contradictory scientific evidence alone remains a visible finding, provided the declared action prerequisites are met.

Revalidate the existing original provider budget and retained reservation/settlement through Planning-owned interfaces. Deriving demand does not reserve again or refund a settled call. Tool execution budgets remain Runtime admission authority. This unit does not invent a new spend policy or automatically call a live provider.

## Transport and durability

Use configured authenticated loopback origins and compiled routes; model text cannot choose hosts, methods, credentials or paths. Bound total time, call count, per-response and aggregate bytes; reject redirects, malformed/duplicate/nonfinite JSON and mismatched receipts. Distinguish absent readback, denial, conflict, explicit rejection and unknown transport outcome. Retain original command bytes for reconciliation; no automatic retry with a new identity after a lost reply.

B2.03 must persist intent and outgoing bytes before any save/validate effect. Peer calls occur outside SQL transactions. A pure request or successful loopback probe is not proof of durable origin. The transport accepts a caller fence guard before sending; the later journal owns that guard and crash recovery. No production coordinator may bypass the journal simply because the client is implemented first.

## Exit evidence

Module-owned tests cover exact numeric command profiles, stable identities, changed payload conflicts, all receipt states, foreign/malformed readbacks, accepted-invalid compilation, selected-only freshness, expired eligibility, current processing denial and unchanged accounting. Loopback probes establish transport bounds only. Fresh isolated Planning installation must exclude peer implementations. Actual installed Runtime/Registry compatibility uses fresh synthetic identities in retained owner stores, with no reset or old migrator. Durable lost-reply, competing dispatch and replacement proofs belong to B2.03/B3; real scientific and live-provider claims remain separate gates.
