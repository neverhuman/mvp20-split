## Explicit edit profile

The existing ExtractionTask/v1 has no selected assertion revisions, and ExtractionDraft/v1 cannot name corrections, retractions, merges or entity-context revisions. Keep all published v1 schema bytes, task hashes, observations and traces unchanged. Add an explicit task/v2 root and an edit-draft profile with payload schema_version2; do not derive an edit from diagnostic prose. Task v2 selects exact existing assertion revisions in addition to the existing entity selections and pinned base head. Every selected revision must belong to the target graph and be verified against the actual pinned owner snapshot before use.

Draft v2 keeps attributed entities/assertions and distinct Research candidates. Entity candidates gain an explicit nullable context Artifact reference. A closed edit union names correction, retraction, merge and entity-context revision. Corrections and context revisions point to an exact accepted prior revision plus a replacement candidate local ID; retractions name an exact assertion revision; merges name exact source/target entity revisions. Each edit has its own attribution and stable local key. Referenced replacement candidates are consumed as replacements, never also emitted as additions. Ordinary unconsumed candidates can become additions after validation. The validator rejects duplicate targets, conflicting replacement ownership and unknown/ambiguous references with item-specific findings.

Use a separate reviewed v2 prompt with typed edit examples and an explicit instruction to retain unresolved targets. Models select from supplied references; guessed entity IDs or prose claims of prior acceptance have no authority. Provider output remains in the existing bounded TypedProposal/TaskProviderObservation-v2 envelope. The closed output catalog selects a draft parser from the exact pinned schema. Trace projection preserves attribution paths for edits and their replacement candidates without claiming that an edit was accepted. Raw captures and canonical typed payloads keep their existing64KiB bounds. Old task/observation readback must remain byte-exact. Inspect the existing SQL size/identity constraints before deciding whether a migration is needed; versioning alone is not a reason to mutate persistence.

## Validation and partial progress

Validation combines the exact observed draft, byte-verified source bundle, actual pinned Knowledge snapshot/vocabulary/policy and a published interpretation Artifact. Neither model-proposed match lists nor a locally well-formed head prove owner state. Foreign, unavailable, stale or differently hashed owner records cannot become proposal authority.

Check quote bytes and source selection separately from semantic entailment. Resolve candidate references only when their explicit targets and selected owner facts agree; retain multiple matches and label/alias collisions as unresolved. Preserve negation, hypothesis/unresolved posture and missing context. Required context cannot be silently fabricated from labels or inferred scientific defaults. Deterministic IDs for newly proposed objects bind scope/task/local identity, while accepted prior identities remain exactly pinned.

Produce item-specific findings and withhold structurally invalid operations plus dependent operations; unrelated valid exploratory candidates may progress when their complete proposed batch satisfies the public owner contract. Low confidence, weak science or contradiction alone is not a global quality veto. An unsupported claim must not become an accepted citation or an inferred value become source-stated fact. Capacity, permission, exact revision and mandatory structural-context rules remain explicit prerequisites. Do not silently truncate an oversized operation batch.

## B2.01c public read binding

A focused Planning Knowledge reader will use authenticated public POST reads only, with a closed route set, bounded response bytes and one whole-review wall-clock budget. It will bind the exact authoring profile and, for an existing graph, the selected immutable snapshot and accepted change. The accepted change must name the same resulting snapshot, position, policy and graph as the pinned head. Read failure, scope denial or mismatched bytes cannot fall back to fabricated context. The reader must verify every selected entity/assertion revision exists in the pinned snapshot, while candidate validation distinguishes stale edit targets from historical references.

A newer live head does not replace the task's selected head. Genesis profile discovery is only an observation; final acceptance still checks the base and pinned profile. Existing immutable profile/snapshot/change reads require no mutation or access to peer SQL. Grounded prompt preparation adds the exact closed output schema, operation schema, vocabulary and selected graph facts as data to the separately pinned instructions/source packet. It must retain explicit record identities and a hash of the pinned context, reject overflow without truncation, and avoid interpreting owner labels or source text as instructions. This bounded packet is not a tokenizer/context-window or live model quality guarantee.

Verification distinguishes loopback protocol adversaries from a separately installed actual Knowledge host and Planning client. Historical reads must survive a newer head and owner restart, and scope/grant failures remain explicit. Synthetic accepted fixtures can establish read compatibility; they cannot establish source rights, scientific validity or production acceptance of Planning proposals. B2.03 remains responsible for actual proposal acceptance and typed accepted-log replay.
