## Policy and eligibility

Runtime owns a focused supervision_policy module. Its private versioned record binds tenant/project, exact compiled plan hash, up to64 authored checkpoint rules and aggregate checkpoint/request/model-call ceilings. Each rule names a static node address, optional named scalar fields, at most255 additional node reads, a bounded deadline, per-slot request/call ceilings and an explicit fallback (continue unchanged or block only the target). No endpoint, credential, executable expression or arbitrary code belongs in this policy.

Invoke rules are review-only and have no adjustable fields. Materialization rules name existing inline fields whose compiled input types are scalar. Numeric fields have exact unit/type and finite closed decimal bounds. Boolean/string fields have a finite allowed set. Runtime rejects missing fields, reference/Artifact/collection fields, widened types, wrong units, reversed bounds, duplicate selectors and unbounded policies. A current value outside the adjustment range is not itself rewritten: fallback preserves the original input, while a proposed value must satisfy the declared range. Existing conversion schema validation remains mandatory after an accepted change.

Rules resolve against the authored body and compiled interfaces. Selected reads must be in the target's own authored scope or an ancestor scope so a concrete target occurrence determines their exact loop/scatter context. This prevents implicit wildcards or accidental selection of a different iteration/member. Runtime must still prove actual membership, active ancestors, selected observations and absence of issued work under the run lock.

A reviewed policy owns canonical bytes and a hash. Named rules, fields and read selectors sort canonically; no caller mutation can alter a retained policy. Private record validation is separate from domain policy behavior. Pure eligibility neither grants provider authority nor establishes that an Artifact exists or a scientific proposition is true.

## Admission and concrete checkpoints

Admission selects an exact reviewed policy for the exact reviewed graph. Pin its bytes and identity atomically with the run before initial ready Invoke materialization. Existing unsupervised admission keeps its behavior. Additive admission transport must avoid the public graph-runtime -> supervision dependency cycle and preserve existing command receipts. Operator/human edits affect later admissions only; no policy replacement route is introduced for active runs.

A coordinator hook runs before target invocation materialization or binding-intent opening. It resolves a stable slot for each concrete occurrence, opens it once under the owning run transaction, applies campaign-wide ceilings and records its deadline bounded by the original run deadline. Only selected target work pauses; unrelated branches and ordinary deterministic coordination continue. Retain the original relevant observation set rather than treating every global revision as stale. A terminal slot never reopens.

Request/outbox creation must share the owning transaction when invoked from a coordinator; do not call a second run-locking transaction while holding the first lock. Network I/O remains outside SQL. Context/model preparation and call issuance remain Planning-owned; policy counters are ceilings, not proof of payment or refunds.

## Ordered implementation and proof

c.i implements the pure private policy/eligibility boundary with module-owned tests, exact decimal/type/unit checks, authored-path/read-selection checks and immutable reconstruction. c.ii implements atomic admission pinning and compatibility. c.iii integrates concrete checkpoint creation and target-only holds. B2.01d independently proves SQL fences, original replay, nested occurrences, relevant refresh and unrelated progress. B2.02 atomically commits winner/effective fields/audit/outbox, and conversion opening/revalidation must use the same immutable effective-value resolver.

Missing live provider configuration is not a blocker for these deterministic gates. No routine human approval is added during a campaign. Weak or contradictory science remains an explicit observation; it does not become a global quality veto.

## Admission integration detail

c.ii is delivered in three equal prerequisite units: a explicit supervised admission command and immutable policy catalog; b forward schema and atomic policy pin/reconstruction; c admission integration and actual SQL replay/rollback proof. The separate `graph.admit_supervised` numeric-v2 command carries the existing graph admission record plus the exact reviewed policy digest. This avoids silently selecting a policy from mutable configuration and preserves original graph admission parsers and receipts. Runtime uses an exact scope/plan/policy lookup; no policy bytes or arbitrary instructions are accepted through this public command.

The immutable pin belongs to the run transaction and precedes ready-node issuance. Until c.iii supplies checkpoint scheduling, pinned targets remain unissued through a focused eligibility guard in admission and advancement; unrelated nodes retain normal scheduling. No public HTTP activation is implied by a domain admission method. The original command receipt must replay before catalog access, including after configuration replacement. An unsuccessful admission leaves no run/policy pin or dispatch intent. Policy storage is append-only; cancellation and later campaigns do not mutate the admitted bytes.

## Concrete checkpoint creation

c.iii has three equal units: a immutable concrete checkpoint snapshot/identity; b transaction-local append-only slot storage with actual membership, checkpoint ceiling and deadline checks; c admission/advancement integration and focused SQL proof. B2.01d retains independent race/recovery acceptance. The Runtime-private supervision_checkpoints module owns this boundary.

A checkpoint binds the run, admitted policy hash, authored rule, concrete activation and exact original selected observations. Identity is deterministic over those pins; later global progress cannot create another slot for the same occurrence. Snapshot reconstruction must preserve original state/output bytes. Creation leaves the graph node ready and unissued, avoiding self-induced observation staleness. Active ancestor/membership checks and absence of Invoke/binding intents are required under the same run transaction.

Admission creates initial ready checkpoints after the complete root frontier exists and before issuing work. Advancement creates a checkpoint once a selected concrete node is ready, including later loop/scatter scopes. A repeated pass loads the original checkpoint without refreshing its deadline or observations. Unrelated nodes continue normally. The run deadline bounds the checkpoint deadline.

The policy checkpoint ceiling bounds request-eligible slots. Additional occurrences retain an explicit fallback-required record with checkpoint_limit_exhausted; this diagnostic record does not grant another request or model call. All records remain bounded by the graph activation limit. Per-slot and campaign request/model-call ceilings remain pinned; reservation/consumption occurs at the later request/call gate. Expiration and fallback do not themselves accept execution here: B2.02 owns the atomic terminal winner and release/effective-value decision.

The durable checkpoint is the pending context-preparation work item. It is not a Planning request: exact Planning context/prompt/model Artifact references must be prepared before forming that public request. B2.03 bridges pending checkpoints to the existing request journal; when doing so, request/outbox creation and slot accounting share the owning run transaction. This avoids fabricating context or provider authority during graph advancement. No live provider choice is needed for checkpoint creation.

The integration review identified that node state/output observations alone do not capture the original materialization scalar fields required by the approved correction. c.iii.c therefore also captures exact named scalar values under the run lock and exposes their digest. A new private checkpoint seed v2 retains these values; the committed v1 reader remains closed and readable. Original values may be outside adjustment bounds and remain valid unchanged fallback inputs. Only new proposed values must satisfy the adjustment bounds. No existing seed bytes are rewritten. B2.02 must require the original scalar-bearing profile before applying an adjustment; legacy observations alone cannot authorize that effect.
