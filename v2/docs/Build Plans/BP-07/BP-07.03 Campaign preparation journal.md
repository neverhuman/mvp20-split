## Ordered units

Four equal implementation units within c: i byte-owned preparation record and readback validation; ii forward migration and immutable journal; iii PostgreSQL authority/replay/race/rollback checks; iv independent installation/restart/replacement proof. All start0%. Design writing earns no credit. Finish each unit before dependent work. B1.03d owns full actual-owner preparation integration; B2 owns compiler/eligibility and dispatch orchestration.

## Owned objects and retained data

Campaign preparation has one immutable identity per scoped engagement, bound to the exact original RequestSnapshot. Provider retries reuse the same prepared bytes; a materially different context requires a new engagement rather than overwriting history. This does not re-pin a running campaign or supersede its receipts. Fresh rights or relevant-owner checks can refuse new processing without mutating the retained preparation.

Use focused private objects for packet evidence, input-selection summaries and the complete preparation record. Packet evidence owns exact canonical packet bytes, packet SHA/length, fixture tokenizer/configuration and measured fit. Input summaries own original plan SHA and each ordered candidate's lane, exact identity, payload hash, required flag and inclusion disposition. The packet already retains exact included payloads, consumed observations and original/budget omissions. Do not retain a second copy of every omitted Artifact body or the entire128MiB pre-packing plan.

The factory accepts a validated CampaignSlicePlan and successful prepared packet, reruns deterministic packing outside SQL and checks equality before creating the immutable record. Unavailable preparation is not a successful stored packet. Strict private manifest decoding rejects duplicate JSON keys, nonfinite values, unknown profile/fields, malformed hashes and oversized input. Canonical roundtrip and redundant field comparisons catch accidental corruption or conflicting histories.

Readback verifies exact stored packet hash/size, closed packet profile and reviewed instructions, original request identity/canonical content, tokenizer fit and output reserve, candidate inclusion/omission coverage, required presence and consumed-observation correspondence. Revalidate included Artifact bodies and roles against original references. Every duplicated SQL identity/fingerprint must agree with the validated record. Historical readback need not fetch omitted bodies or assert that source rights remain valid. Re-running full candidate packing remains possible when the caller supplies the original validated plan, through the existing reconstruction function; do not claim omitted-body reconstruction from metadata alone.

Bounds: packet bytes at most8MiB, candidate count at most900, canonical manifest at most2MiB. Reject overflow explicitly. These are private storage limits, not expanded public source/profile or model budgets.

## Forward migration and write set

Add planning_0012 with one new `planning.campaign_preparations` table. Columns: scoped tenant/project/engagement key; exact request SHA; preparation-manifest SHA; original plan SHA; packet SHA; canonical manifest bytes; exact packet bytes; database registration timestamp. Primary key is scoped engagement. Foreign key includes scoped engagement and request SHA referencing existing immutable planning.requests. SQL checks bound byte lengths and SHA syntax. Grant service SELECT/INSERT only; no update/delete, mutable control table or peer-state access. No existing row rewrite or migration backfill.

Use the existing explicit migrator. Imports and serving code never migrate. A second upgrade is a no-op. Downgrade raises a forward-migration requirement. Once0012 is installed, Planning<=0.47 migrators must not be run there; older readers that do not use this table retain their prior immutable history. Rollback means stopping the new workflow while retaining rows and deploying a compatible reader, not dropping preparation history.

Journal register requires trusted principal `record_attempts`, exact scope and original actor. Bind/re-render before opening the transaction. Acquire the established family-before-request lock order through the existing helper; campaign preparations reject extraction-family membership. Read and verify the original request and its campaign/supervision purpose. On an existing preparation, exact replay returns original bytes and timestamp; changed contents conflict. Otherwise reject if any provider dispatch or observation already exists for that engagement, then insert the one preparation row. Unissued reservations may exist, but are not modified. Failed validation or insert rolls back the whole transaction. No peer/filesystem/provider call spans a SQL transaction.

Read requires `read_attempts`, original actor and scope. Return explicit absence for an authorized known engagement with no preparation; distinguish that from corrupt data, foreign ownership and missing request. Never translate denied reads to a fabricated empty packet. Existence or replay of a preparation is not permission to dispatch, issue another attempt, widen spend or renew source processing.

## Issuance and correction boundary

The new journal alone does not change the legacy generic/extraction dispatch protocol. Subsequent campaign orchestration must require the exact stored preparation, current processing checks and existing budget/issuance fences before a call. Document that integration as pending until its owning gate passes. Source/Registry/Knowledge observations are versioned context, not leases. Corrections remain future-campaign-only; do not add active receipt invalidation or a scientific-quality veto.

## Required evidence

- Pure records: successful exact roundtrip; malformed/corrupt/oversized manifests; changed request/profile/packet/read-set/omission/required-body rejection; fixed predecessor compatibility; retained omitted metadata without copied source bodies.
- SQL: explicit forward/idempotent migration, service privileges, actor/scope denial, unknown request, exact replay preserving timestamp, changed preparation conflict, no late first insert, unissued reservation compatibility, corruption detection and transaction rollback.
- Races: separate connections competing same/different preparations and registration versus dispatch under the same request lock. First committed preparation wins; no partial record or post-issuance first registration. Existing dispatch history is never retroactively labeled prepared.
- Independent proof: current wheel only, serial opt-in PostgreSQL, fresh synthetic engagement identities in retained fixtures, process exit/restart and second installation readback preserving exact packet/manifest hashes and registration time. No reset, deletion, old migrator, peer private import or overwriting prior evidence.

Owner source rights, full actual-owner packet construction, real provider framing/quality, scientific efficacy and target-host deployment retain their later gates.
