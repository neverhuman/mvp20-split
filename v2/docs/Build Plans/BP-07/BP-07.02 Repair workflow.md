## Delivery boundary

Use two equal gates within the existing B2.02c weight: i immutable feedback and repair-request construction; ii family-enrolled bounded execution, fresh public input verification and independent process proof. Both start0%. This refines the existing milestone without increasing its parent weight or starting implementation before b passes.

Feedback is machine-readable diagnostic input, not new permission. The same root actor, scientific pins, objective, model/configuration, prompt, output profile and reviewed policy govern every step. A repair never silently changes source revisions, graph head, known questions or method applicability. Scientific contradictions, low confidence and partial utility are not blanket rejection conditions.

## Feedback and exact input binding

A focused repair feedback object binds the exact persisted parent trace, parent task/request and observed output identity. It retains bounded typed findings and the distinction between malformed output, missing operational input, unresolved interpretation, partial useful proposals and deliberate abstention. Include explicit prior-output completeness and exact bytes or a lossless bounded encoding when needed to repair malformed syntax. Model text and diagnostic messages stay data, separate from the pinned instruction template.

Use a packaged, digest-pinned feedback content schema. Canonical bytes, deterministic identity and a size limit make a repair reproducible; overflow is explicit, never truncation. Feedback does not label a candidate accepted. Keep earlier valid proposals and unresolved findings available even when a later attempt is worse or the family exhausts its allowance.

Request construction preserves all original context and permits only explicit additional result entries for parent interpretation and diagnostic context. It must fail before dispatch if input-count or context-size ceilings cannot accommodate those entries. Child identity derives from exact parent/feedback bindings, so retrying the same prepared step cannot silently create a new engagement or replenish budget.

A proposed ArtifactRef is not proof of publication. Before execution, bind exact published interpretation/feedback records through fresh public Data processing-content reads and verify bytes, schema, scope and identity. Historical references are not reusable rights grants. Data publication/receipt ownership remains separate from Planning interpretation and Research/Knowledge acceptance. Do not claim an integrated automatic publication loop while its producer is absent; the execution boundary must explicitly require those published inputs. B2.03 owns subsequent authoritative owner handoffs.

## Durable execution and recovery

Register the exact child request/task, enroll it against the persisted parent and root family, then use the existing physical reservation/dispatch/settlement path. A trace pointer alone cannot authorize a call. A prepared repair step exposes concrete verified diagnostic input to its adapter; metadata-only reference attachment is insufficient evidence that a model receives the findings.

Each repair step consumes a bounded physical attempt and retains its immutable observation/trace. A retry of the same step resumes that attempt, including pending/unknown state, rather than creating a fresh child. A bounded chain driver may request another prepared step only within the original family ceilings. Membership-change reconciliation retries the unchanged operation with an explicit local bound; it cannot acquire reversed locks or invent a replacement root.

Keep external reads, adapter calls and publication outside SQL transactions. Preserve the distinction between an unavailable diagnostic Artifact, an unexpired pending call, a recorded unknown outcome, useful partial output, abstention and exhausted admission. Missing authority or exhausted budget ends the bounded effort with retained progress; it does not create a human wait inside an active campaign.

## Required evidence

Pure cases prove canonical feedback, exact parent/output binding, malicious text kept as data, input overflow, deterministic child identity and unchanged root authority. Owned PostgreSQL cases prove enrollment before dispatch, immutable retry, bounded chain exhaustion, pending recovery and preservation of useful earlier results. Provider fixtures must inspect the actual diagnostic packet, rather than merely return a predetermined answer without seeing it.

Actual Data reads must distinguish allowed current processing, denied rights, missing input and wrong bytes/schema. Independently installed Planning processes must preserve prepared step identity, family membership, charges and traces across replacement. These are software boundary proofs; provider quality, real scientific labels and live model/egress configuration remain later gates.
