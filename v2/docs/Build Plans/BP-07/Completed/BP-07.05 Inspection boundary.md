## Read surfaces

Configure the new routes only with Runtime supervision plus existing inspection/cursor configuration. Reuse the reviewed persistent HMAC cursor key; no ephemeral implicit key or new authority. Existing exact /v1/supervision/decisions/{run}/{decision} remains available and unchanged.

Under /v1/supervision/runs/{run}/checkpoints: list checkpoint summaries, then /{decision}/requests, /{decision}/requests/{request_sha}/context and /{decision}/requests/{request_sha}/responses. Page size1..10, explicit totals/continuations. Index records identify original checkpoint, activation targets, request count, original eligibility reason and committed winner kind/reason (if any). Requests expose original lineage/engagement/model/prompt/limits, compact retained execution-attempt statuses/hashes, report stop reason, response count and Runtime disposition/reason. Context pages distinguish included entries and omitted Artifact metadata/reasons; no content fetch. Response pages expose original identity/status/reason/attempt/output digest and capture Artifact reference plus whether it matches the immutable winner. A retained proposed response is not automatically rejected or accepted.

Do not expose raw prompt/source/capture bytes, lease secrets or peer credentials. Runtime can report only completion/response evidence it has actually retained; missing report means unobserved here, not proof that no call occurred. Full live Planning diagnostics and scientific quality/claim review remain their owning successor surfaces. Existing public exact decision remains the authoritative effect read. UI distinguishes pending, model proposal, owner rejection, fallback/cancellation and accepted effect.

## Consistency and boundedness

Each request uses an owned read-only repeatable-read transaction. A signed inspection snapshot binds scope/run/current run revision and a digest of immutable table counts for checkpoints, requests, received responses/reports, Runtime dispositions and winners. Including supervisor counts is necessary: a response can arrive without graph topology/revision changing. Any relevant appended history or run revision change invalidates old snapshot/page tokens with explicit409 resnapshot. Never claim a retained historical frontier or silently combine generations. Tokens preserve existing expiry/scope/resource/mode checks and survive configured-key process replacement.

The checkpoint page issues the snapshot token; dependent request/context/response pages require it. Page cursors additionally bind the selected resource and offset. A terminal unchanged run can be paged after replacement; an active changing run may require refresh. Counts and SQL selection are transaction-coherent; rows are reconstructed through owning domain objects and explicitly mapped to public DTOs. No network inside SQL, cross-owner SQL or execution mutation. No arbitrary filter/query language; page identity is stable and deterministic.
