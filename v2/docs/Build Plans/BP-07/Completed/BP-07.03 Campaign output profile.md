# Campaign output profile design

- Design status: scoped B1.04 implementation design; no implementation credit.
- Baseline: Planning0.49, public Planning0.8,508 published predecessor schema files, planning0012.
- Canonical owner: [BP-07.03 tracker](BP-07.03%20Campaign%20proposals%20and%20context.md).

## Ordered units and compatibility

B1.04 has four equal units: a additive public draft/schema profile; b pure request-bound candidate/parser objects; c provider observation and durable readback integration; d isolated installation and predecessor compatibility proof. All start0%. B2 separately owns semantic evidence-link, selected-tool, applicability, compiler/eligibility and handoff policy. New topology targets future campaigns; no user approval ceremony or active campaign mutation is added.

Publish a distinct `planning.campaign-draft/v1` schema, not a new interpretation of reference-only or extraction output. Add public Campaigns as an explicit Planning-contract dependency for ExecutableCampaignV4 and existing finite scalar constants. Preserve all508 predecessor schema bytes, original profile hashes, TypedProposal/v1, ProviderObservation/v1 and TaskProviderObservation/v2. Reuse TypedProposal and task observation only for the new profile; existing observations remain decoded through their original profiles. Do not change numeric command encoding or existing receipt replay.

## Typed proposal data

CampaignDraft carries schema version, action, rationale, original decision-scope digest, explicit proposal-only/scientific-not-established authority, optional candidate, bounded evidence requests, alternatives and unresolved points. Actions are abstain, request_evidence and propose_campaign; Knowledge changes remain in their existing reviewed output profiles. No arbitrary Python/handler, accepted measurement, signed constraint mutation, command identity or execution acceptance is representable.

Candidate is a discriminated union:

- Future campaign: title, existing ExecutableCampaignV4 definition and expected evidence intents. The actual Runtime compiler remains authoritative for the graph; structural JSON validation is not compilation.
- Declared adjustment: exact GraphReadCut, at most64 scalar input changes and expected evidence intents. Each change names an authored scope path/node/input, expected previous-value digest and proposed existing finite ScalarConstant. These are bounded proposals, not new Runtime commands, arbitrary JSON patches or permission to modify an active run.

Evidence intents name exact question, need and assessment selections, optional producing node, expected evidence description and uncertainty. Alternatives retain compact descriptions and reasons; unresolved points name optional question/need plus missing/unknown/weak/contradictory/inapplicable posture. These fields preserve ideas and uncertainty, not scientific conclusions. Reference scope, actual selection membership, question/need relationships and producer-node meaning are validated by their owning policy layers; a wire DTO does not grant authority.

## Pure parsing and original-request binding

Use focused CampaignDecisionScope, CampaignCandidate and CampaignOutput objects. The decision-scope object binds the original request's digest/purpose/runtime cut; echoing the digest does not authorize a change. Parser accepts bounded strict UTF-8 JSON with duplicate/nonfinite/deep/malformed input rejected, validates only the new profile, and preserves exact raw provider capture separately from normalized typed proposal bytes. Keep the existing65536-byte capture/typed payload limit.

Require original campaign/supervision purpose, output-schema pin and allowed action; exact decision digest; consistent action/candidate/evidence-request shape; same-scope references throughout definitions/intents/unresolved points; and exact original Runtime cut for adjustment proposals. Reject adjustment output without a supervision cut. Do not treat this as validation of permitted adjustment targets/ranges: B2 must bind a reviewed declaration and BP-07.04 owns Runtime engagement acceptance. Unknown/weak scientific content remains visible and does not create a global quality veto.

Future graph and adjustment candidates remain distinct from compiled plans, owner-accepted evidence and dispatch authority. Relevant read-set comes from the consumed preparation, not a model-selected arbitrary read-set. Later policy combines the parsed candidate with that exact preparation and reviewed capability universe.

## Reconciled Runtime limitation

Existing public Runtime has SaveDraft/ValidateDraft for ExecutableCampaignV4 and immutable GraphReadCut observations. It has no parameter-adjustment write API. B1.04 therefore adds a proposal representation only, preserving this visible acceptance gap; it must not manufacture a successful adjustment receipt or reuse an unrelated command. Runtime adjustment application requires its separately scoped later engagement boundary. The original decision_scope is currently a digest, not a complete decoded target/range declaration; later policy must supply and verify that declaration before eligibility.

## Exit evidence

- Additive schema/fixtures: valid future, adjustment, evidence request and abstention; malformed discriminators, arbitrary handlers/accepted-result fields, missing required values, bounds and scalar strictness; all old schema hashes unchanged.
- Pure candidates: action/purpose/scope/cut/digest rejection; duplicate/conflicting change identities; request immutability; deterministic canonical payload; bounded malformed provider data and visible unresolved science.
- Integration: new typed observations roundtrip through existing capture/journal paths without changing reference/extraction behavior; fixture provider output support is deterministic software evidence only.
- Independent acceptance: isolated wheel/public-contract installation, module-owned tests, exact predecessor observation/schema/receipt replay, and scoped SQL tests only where durable decoding changes. No live provider, model-quality or scientific-validity claim.
