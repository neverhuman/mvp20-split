## Next Validation Boundary

A save creates a revision, not a validation or run. definition.validate names draft_id, revision and content_sha256; the server loads that exact retained revision and its configured reviewed tool/schema universe. It compiles without I/O using the existing compiler, then commits an immutable validation record and original command receipt. A structural finding is a successfully recorded validation result, not a lost command or an accepted campaign. Missing/foreign revision or mismatched digest rejects the command.

Validation records pin universe_sha256 and the exact compiled plan hash or bounded findings. Saving later edits cannot mutate them. Validation may inspect an older retained revision, but activation must require the explicitly selected current draft head plus matching validation/content/universe; no implicit rebase. The immutable validation store may retain the compiled plan and required public descriptor/schema material needed for replacement; no request-supplied arbitrary schema URL is fetched.

The configured reviewed universe is separate from the live Registry lifecycle. Registry-driven UI forms use public descriptors and exact pins; validation cannot silently admit an unknown release because its JSON shape resembles a reviewed one. Current eligibility, permission, budget and the one-active-campaign guard are activation checks. A structural validation record explicitly leaves scientific applicability/acceptance unestablished. Broader scientific validation requires its owning services.

For dynamic draft admission, extend the existing Runtime admission path with a scoped verified plan resolver and draft validation guard; do not add a second scheduler or run database. Resolve external observations before the short transaction; recheck owner-local draft/validation/eligibility cut under the existing admission guard. Return an original pending/rejected/accepted command receipt and preserve old configured-plan admission behavior. Publication/activation of a draft must have an explicit idempotent command and versioned contract, not implicit side effects of GET or save.


### Publication and execution integration watchpoint

GraphAdmission and binding execution currently resolve only the configured PlanCatalog. Saving or compiling a draft cannot make that process-local catalog discover a new plan. A publication adapter must retain the exact validated plan, public tool metadata and schema material under Runtime ownership, preserve immutable compiled identity across restart, and supply the existing plan-resolver port to admission/binding execution. Merely inserting a graph_plans row is not an eligibility grant. Historical published material must remain readable for already-admitted runs even when later policy refuses new admission.

Use a bounded derived cache only for immutable compilation material; current activation eligibility cannot be cached as permanent authority. Configuration/Registry changes require explicit revalidation/current eligibility checks. Avoid a second compiler implementation or a parallel execution state machine in the authoring module. This is part of the scoped B1/B2 integration work, not a new service or an external user decision.

### Admission versus retained execution material

The next adapter must expose two distinct decisions: locating immutable material for an already-admitted run, and authorizing a new admission. A general graph.admit request must not gain permission merely because a prior draft validation or run retained the same plan hash. Keep configured-plan admission checks intact; draft admission must name the exact draft revision/content, validation and plan and pass the draft-specific guard. Binding execution may restore retained schemas for its already-admitted plan even after current configuration no longer permits a new run.

Draft admission should commit the retained publication reference, run/frontier and original execution receipt in the existing GraphAdmission transaction. Preserve pending/rejected/accepted replay semantics and the existing one-active-campaign guard. A restart must rebuild from retained material and verify the compiled hash; it cannot require the old process-local catalog or silently recompile against new schemas.

The form surface will need both public Registry descriptor observations and exact reviewed schema material. Primary action: save a next-campaign draft, then request pinned validation. Admission remains separate and unavailable until its owner policy is implemented. Unsupported schema constructs produce an explicit unavailable editor with inspectable technical detail, not guessed controls or a silent JSON-shape change. Layout coordinates stay separate from executable definitions. Show a comparison panel on demand with changed nodes, edges, bindings and affected context; do not claim scientific compatibility from a structural diff.

DraftSession owns base revision, local draft, selected node and dirty state. A dedicated authoring transport owns bounded public DTO decoding and canonical command identities; components never issue competing requests. Save/validate each retain their original command identity until a terminal receipt is reconciled. New local edits invalidate the displayed validation for activation but preserve old results as historical evidence. An older save response may update its acknowledged base only without overwriting newer local edits; conflicts keep both the local draft and authoritative head available for deliberate reconciliation.

Loading the draft list does not erase an existing draft; an empty list offers a bounded new-draft action. Partial capability/schema availability identifies the missing selection and disables only dependent actions. Stale reads retain visible local work but mark validation out of date. Authentication/scope denial clears protected server projections and disables transmission; session changes must not send an old draft into a new scope. A failed or timed-out command is unresolved until the original receipt is checked, not immediately resubmitted with a new identity. Success shows the committed revision and exact validation binding. Browser failure tests must cover edits during pending saves, stale/denied responses, lost acknowledgements, conflict preservation and focus restoration at desktop and narrow widths.

If a browser-computed fingerprint is introduced, prove it against independent published canonical-command fixtures before using it to accept or reject a receipt. Lost acknowledgement is not permission to issue a fresh command.
