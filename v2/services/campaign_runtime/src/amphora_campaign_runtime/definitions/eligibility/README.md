# Draft tool eligibility observations

Status: BP-05.03/B2 verified; scoped tests and installed actual Registry integration passed. Owner: Runtime definitions. [Parent boundary](../README.md).

RegistryEligibility is an optional server-side adapter for exact Registry resolve commands. Host configuration `draft_registry` requires authoring, an explicit HTTPS or loopback HTTP origin, token environment variable and Registry actor. Credentials never reach Studio or audit records. No redirects/proxies, 256KiB response bound, at most the reviewed universe's64 releases, ten-second observation collection budget checked before/after each request with bounded socket timeouts. This is not a hard wall-clock cancellation guarantee for a stalled streaming peer.

Requests use exact reviewed locks/descriptors/ports. Default synthetic materials retain `synthetic-tests`; explicitly configured structural materials use their pinned `supplied-finite-molecules` context and require the Registry structural-mapping reason. It does not assess biological/material science or promote evidence. EligibilityObservation checks matching scoped release, descriptor, active lifecycle, structural/scientific/capacity/policy statuses and a positive expiry window. A candidate is an observation, never a reservation, selected worker or execution grant.

Preparation occurs outside the Runtime transaction. Runtime then rechecks head/universe and observation freshness using its database clock under the existing admission guard, alongside budget/inputs/one-active-campaign checks. Default maximum observation age is5 seconds, explicitly configurable1..60, and the Registry capacity expiry always also applies. Future-dated, stale or expired evidence rejects. Remote lifecycle/capacity may change after observation; there is no cross-service atomic reservation/revocation guarantee. Runtime claim/fence/acceptance authority remains separate.

Unavailable, denied, malformed or incompatible Registry observations produce a terminal rejected Runtime admission before any run/frontier/publication effect. Registry resolve has no reservation or execution effect to reconcile. Each unfinished preparation may obtain fresh resolve identities; replay of any terminal Runtime admission does not call Registry again. A crash before the Runtime commit retains the original pending Runtime identity for safe recovery. Accepted admission records original Registry identities, request digests and complete public receipts in Runtime's immutable audit_events transaction alongside publication/run/receipt. No new table or public schema is introduced.

Tests: `tests/definitions/test_eligibility.py` owns pure policy and actual loopback HTTP transport probes; `test_eligibility_admission.py` owns PostgreSQL guards, expiry/unavailability/replay/rollback, active-run and stale-head checks. Host configuration is in `test_http.py`. Scripted Registry candidates prove the consumer policy, not actual Registry admission or scientific correctness. Replacement must preserve immutable evidence, terminal replay and absence of peer I/O under owner locks; live peer/replacement proof remains B2/B3/V1.
