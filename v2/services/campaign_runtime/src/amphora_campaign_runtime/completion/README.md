# Runtime Completion Boundary

- Status: BP-02.05/D1-D3 preparation, atomic acceptance, retention proof and stale-intent recovery implemented; delivery/closeout remain D4-D6.
- Owner: Campaign Runtime, private `runtime` schema. Architecture: [runtime protocol](../../../../../docs/Architecture/System/Runtime_Command_Protocol.md).

CompletionProposal owns semantic profile 1: SHA-256 of sorted compact ASCII JSON containing profile, scope, actor and normalized CompleteInvocation payload. Command ID/transport credentials/derived reservation receipts are excluded; changed semantic outputs change this digest. Canonical command identity remains independently authoritative. PreparedIntent derives stable bounded output labels from SHA-256 of `output:<port>` or `checkpoint`; full descriptors accompany every label, so labels never substitute for metadata validation.

IntentPreparation requires configured complete action, matching scope/actor and a current run/worker/attempt/fence/lease. It locks run, worker, activation/attempt and intent before reading database time. It validates output ports/schema and checkpoint revision against the immutable tool descriptor snapshot captured at admission. Optional host `tools` contains trusted public ToolDescriptors; bindings and ports must be unique and pure. Legacy/unconfigured snapshots are empty and cannot authorize completion. Configuration changes never rewrite admitted run contracts.

The canonical command is registered pending, then its immutable PREPARED intent, audit/outbox and run revision commit together. Intent identity equals the stable runtime operation ID. Duplicate preparation reuses it; changed command bytes conflict. Invalid proposals yield stable rejected receipts; previously prepared intents receive irreversible ABORTED proof before terminal rejection. Cancellation/revocation uses the same locks and abort records. Preparation is neither successful execution nor accepted output.

CompletionCoordinator releases all database transactions before contacting ArtifactReservations. The client uses a configured authenticated endpoint (HTTPS or literal loopback HTTP), bounded time/body, no redirects/proxies and deterministic reserve command identity. It validates the exact scope/artifact/intent/output/semantic digest and reserved status. The runtime imports only public artifact contracts, never artifact owner code/tables. A scripted transport peer proves client behavior; actual artifact integration remains D6/.06.

Each verified receipt is persisted in immutable runtime.intent_reservations under its intent/output key. Partial progress resumes without reacquiring saved outputs. Lost responses retry the same remote command. Outage or invalid response leaves the operation pending and the intent protected; it never fabricates abort or release. Cancellation during remote I/O can still acquire owner locks; the returned receipt is retained as cleanup evidence, then a fresh prepare check reports the permanent aborted outcome. The committer rechecks all live authority and receipt bindings at acceptance; terminal proof is public and D4 owns delivery outside SQL.

runtime_0004 adds immutable run.tool_snapshot and owner-only reservation evidence. There are no UPDATE/DELETE grants on either immutable boundary. Service startup checks the migrated shape and never runs DDL. No scientific validity, external-effect execution, general graph compilation or provider policy is introduced.

Tests are local `tests/completion/`, selectable with `dev/run_tests.py --module runtime --area completion`. Oracles include simultaneous duplicate prepare, semantic conflicts, output/checkpoint/fence rejection, whole-transaction rollback, partial receipt recovery, cancellation during remote I/O and expired prepared abort. HTTP client tests reject redirects/mismatched/oversized responses and preserve command identity. A rebuild preserves these profiles, immutable records, grant/lock order, pending/rejected distinction and exact public receipt checks. D4-D6 remain required for complete retention/delivery integration.

## Atomic Acceptance (D2)

CompletionCommitter rechecks configured actor/scope, live run/worker/attempt/fence, database time after locks, pinned output descriptor, activation checkpoint revision, immutable semantic intent and every stored reservation receipt. Missing receipts remain pending; mismatched proof or permanent authority failure aborts a prepared intent with a stable rejection. A global run revision advance caused by an independent activation is not a rejection precondition.

CompletionDecision owns attempt/activation disposition and budget consequences. In one transaction, acceptance inserts the immutable attempt report and any canonical terminal activation result, writes a success checkpoint revision, settles or retains the issued unit, advances run state/revision, marks intent COMMITTED and stores the original receipt plus audit/outbox. A fault anywhere rolls everything back. The committer makes no network/filesystem/tool/model call. Coordination acquires remote reservations before entering this transaction. Endpoints do not accept caller-supplied reservation proof.

runtime_0005 adds attempt_reports because retryable failure must preserve an accepted attempt report without occupying the unique canonical activation result. Every accepted report gets a completion ID; a retryable pure failure requeues only within limits, and its successor uses a higher fence. Canonical accepted_completions remains one terminal result per activation. Abstention completes without a fabricated score; permanent failure stays failed; uncertain effects preserve reserved units and block the run. Successful checkpoints remain artifact references, never mutable inline payload state.

Optional host `artifacts` configuration (`runtime_owner`, `reserve_endpoint`, `token_env`) enables authenticated POST /v1/invocations/complete and reports fixture_completion_available. It requires the worker's complete action and admitted tool snapshots. Default applications retain no completion route. Current HTTP tests use a scripted reservation peer; actual artifact/runtime proof, terminal confirmation/reconciliation delivery and interruption acceptance remain D4-D6/.06. No retention release is inferred from timeout; reservations stay protected until their owner receives authenticated exact proof.

Acceptance tests cover checkpoint/receipt replay, rollback after all writes, two independent concurrent completions, failed-attempt retry followed by success, abstention/failure/uncertainty, wrong or missing receipt, authenticated route activation and a commit observed waiting on a lock that rejects after its database lease expires.

## Retention Proof and Abort Recovery (D3)

POST /v1/completion-intents/outcome is enabled with the configured completion peer. It requires a distinct scoped outcome action and a closed public ReservationBinding. IntentOutcomes returns prepared/unknown or immutable committed/aborted proof. Scope, runtime owner, intent, semantic digest, output label and full artifact descriptor must match. Committed proof additionally requires the exact saved reservation ID. Aborted proof covers the exact semantic binding even if a reserve response was lost before its ID was saved: the entire immutable intent can never accept that output. Wrong binding is unknown, never an inferred abort.

queue_terminal inserts stable artifact_confirm/artifact_reconcile outbox operations in the same transaction as committed/aborted intent state and its audit. Confirmation binds the runtime receipt; reconciliation lets the artifact owner fetch authoritative proof. Delivery identity derives from scope/intent/output/terminal action. Replays add nothing. Invalid saved receipt evidence never authorizes a remote operation. There is no network call in these transactions, and queued delivery is not acknowledged delivery.

Cancellation/revocation, rejected completion and stale-intent recovery enqueue reconciliation for saved receipts. If remote reservation acquisition returns after cancellation, its receipt and a late-reservation audit/outbox entry commit together; it cannot resurrect the aborted intent. Lost reserve responses remain discoverable by artifact-owned reconciliation using exact runtime proof.

StaleIntents performs an explicit maintain-authorized per-run sweep of at most 100 intents, returning a cursor. Under run/work/intent locks and database time it aborts preparation that can no longer accept (expired/stale/non-leased/revoked/non-running), preserving live prepared work. It also terminalizes pending commands whose intents were already aborted by cancellation, without changing the original proof. Every changed batch commits rejection receipts, audit and retention delivery intents together. It does not settle attempts: finish bounded reconciliation passes, then ordinary settlement/reclaim can pass its prepared-intent guard. CLI: reconcile-intents with the same config/actor/tenant/project/run selection as settle, plus --limit/--after. No automatic background scheduler is claimed.

Tests cover cancel-versus-commit linearization, revoked preparations, exact committed proof, lost/late reservation responses, public scope/action denial, bounded abandoned-intent recovery, original proof preservation without caller retries and a fault after terminal receipt/retention queue that rolls everything back. Actual peer release/confirmation and network delivery still require D4-D6/.06.
