# Original request delivery

Owner: Runtime; BP-07.04/B2.03c.i. `RequestDispatcher.run` advances one retained request by one bounded exchange phase using `DeliveryJournal` and configured v1/v2 Planning client. `DeliveryProgress` reconstructs the original command and latest known receipt from owned immutable history. No new public contract, SQL table or serialization profile.

Terminal history replays without a peer, including for an authorized reader. New work requires the original preparer's dispatch authority and exact configured Planning actor/scope/family. A database-clock claim fences dispatch; before each effectful POST the journal rechecks the lease, running graph, concrete selected footprint, original deadline and absence of a committed winner. These short transactions end before HTTP. They cannot make Runtime and Planning one distributed transaction: Planning retains its own idempotency, immutable intake and deadline/call authority.

Lookup the original receipt before submission. A known pending receipt disappearing remains uncertain. Store each receipt before attempting its readback on a later tick. Uncertain peer failures retain closed reasons and preserve the last known receipt; no peer body or credential enters diagnostics. Existing 16-claim/64-event and original deadline bounds apply. Local integrity or current-authority failures propagate, leaving the lease to expire; the later owner loop owns their disposition. No hidden retries or unbounded polling.

This module does not issue model calls, select winners, publish captures, decide scientific quality, prepare repairs or schedule itself. Reads/writes are Runtime-owned only. Replacement must preserve exact original commands, receipt precedence, journal fences, terminal replay and no SQL over network. Tests live in `tests/supervision_delivery`; SQL/socket fixtures prove this boundary, not live model or installed Planning behavior. B3 retains process death and contention acceptance; V1 installed owner proof.
