# Private representation storage

Owning milestone: BP-06.05/B1.03. [Design](../../../../../../docs/Build%20Plans/BP-06/BP-06.05%20Physical%20design.md). B1.03 verified with113 scoped source and391 full installed tests; the canonical plan owns remaining milestones.

`ProfileRegistry` owns immutable scoped registration and digest-qualified reads. `WorkLeases` owns single-flight work registration, DB-clock claim/renew/release. `EncodingResults` owns immutable completion, exact winning-claim replay and private reconstruction. `records` centralizes bounded row decoding and scope/profile/input checks; `claims` groups internal outcome/lease values. All imports stay inside Data or declared public dependencies.

Migration `artifact_0008` adds four private tables. Profiles, work intents and results permit only SELECT/INSERT to the service role. Lease updates are limited to actor, token, fence and expiry; identity and historical rows cannot be deleted or rewritten. Profile id/version conflicts are rejected; a complete scoped work digest separates profile, input and context. SQL foreign keys include scope and exact profile digest. Existing Artifact catalog and source tables are unchanged.

Registration requires `representation_manage`; profile reads require `representation_read`; private work/result operations require `representation_encode`. Hosted representation configuration exposes these grants explicitly; they are not source-use authority. The B1.04 binding workflow authenticates source bytes/current process rights before requesting work and separately publishes each source-specific derived Artifact. There is no HTTP cache lookup, unassociated vector Artifact, cross-scope deduplication or rights inference here.

Claims commit intent and a random lease token before computation. Four concurrent connections for the same work should yield one lease and three explicit busy results. Expired/released leases may be reclaimed with a larger fence. DB time alone governs expiry, and renewal cannot resurrect an expired lease. Encoding runs outside these classes and outside transactions. Locks are short, owner-local and ordered; no network or filesystem work occurs under them.

Completion validates work/profile/input/context consistency, then inserts only from the current unexpired actor/token/fence. A lost completion response replays the immutable result only for its exact winning claim, even after expiry. A stale worker cannot take credit for another winner or replace its bytes. A new authorized private claim can obtain the existing cache hit. Release returns false for stale, expired or completed claims. It retains all work/result history. Fences are bounded safe integers; exhausted fences fail explicitly.

Registry/cache misses, conflicts, invalid references and stale claims use bounded `RepresentationError` codes. Grant denial uses existing Data `UploadError`. SQL failures propagate and transactions roll back; no silent retry conceals an uncertain terminal result. A fresh store instance reconstructs retained domain objects from canonical public DTO bytes and verifies identity again.

Tests are owned by `services/data_artifacts/tests/representations/test_storage.py`: actual PostgreSQL scoped registration, independent-connection contention, DB-clock expiry, reclaim/renew/release, stale actor/token/fence rejection, exact completion replay, immutable grants and fresh-object reconstruction. Service privilege probes are restricted to their unique test scope and always roll back. Run serially with `AMPHORA_TEST_POSTGRES=1`; never reset retained data. Source rights/publication are separately verified in the binding workflow; process death is a separate evidence tier and is not inferred from these storage tests.

Replacement must package migration resources, migrate explicitly before serving, preserve all records and pass these oracles with an independent installation. Data versions through 0.13.0 do not know artifact_0008 and must not run migrations against it. This forward migration has no destructive downgrade. Older protocol peers may not be used as migration tools; choose a compatible new Data installation for subsequent integration fixtures.
