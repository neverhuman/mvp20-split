## Durable generation state

## Projection verification and publication

`GenerationPublication(reads, backend)` accepts a trusted injected `ProjectionAdapter`, never a backend from a public request. `build_and_verify(principal, lease)` checks configuration identity and live lease, materializes exact retained vector Artifacts outside SQL, builds the attempt-private namespace, then inspects actual points. Owner comparison requires exact dimensions/metric, count, unique deterministic ids, full profile/binding references and canonical binary32 vector content. Observation order is immaterial; input manifest order still pins generation identity. Fingerprints include vector digests, avoiding an oversized full-vector canonical document. No backend acknowledgement is treated as content verification.

After inspection, current process rights and the winning lease are checked in a fresh transaction; immutable proof and verified phase commit together. Lost calls can reconstruct proof from the same live attempt. Two same-attempt verifiers converge on one identical proof. Backend uncertainty leaves building state and no authority; a stale namespace remains unselected. Verification metadata pins generation, namespace, token/fence, manifest, projection fingerprint and point count. The private proof reconstruction verifies canonical bytes and actual retained attempt identity.

`publish(principal, lease)` requires retained matching proof, current rights and exact expected PostgreSQL head, then atomically records publication, phase/event and selected head. Competing publishers cannot overwrite a winner. Exact published replay returns original historical success, even after a newer head or rights revocation; it performs no backend I/O and grants no content access. Unselected conflicting generations remain explicit verified work until failed/abandoned or expired. No automatic repinning or scientific-quality veto is added.

## Optional generation and retrieval HTTP

`RetrievalService(reads, backend)` composes existing intents/leases/publication and the query broker. Its advance method performs one claim/build/verify/publish attempt per invocation; a live claim returns current status, and expired verified work becomes truthfully failed. No tokens are returned, no hidden retry loop or namespace fallback exists. Caller retries remain bounded by the retained state and may require a fresh generation after terminal failure.

The optional `/v1/retrieval` router exposes POST `/generations`, GET `/generations/{corpus_id}/{generation_id}?sha256=...`, POST `/queries`, GET `/queries/{retrieval_id}`. Generation writes require representation_manage/representation_read/read; generation history requires representation_read. Queries require representation_read/read. Authentication/action checks precede parsing; strict JSON is bounded4MiB/5s. Busy build state is202, terminal/result success200, missing404, conflicts/pending409, current-rights denial403, malformed422 and backend/storage uncertainty503. Success and owned error responses use no-store. Historical semantics are the owning lifecycle/query contracts, not new authority granted by transport.

Host configuration optionally adds `retrieval: {endpoint, token_env, timeout?}`. Endpoint and finite timeout use the pinned loopback Qdrant profile; credentials are read from the named environment variable. Omit retrieval to disable its routes. It can use retained representation state independently of the representations/acquisition route flags. Host readiness checks SQL tables only and does not contact Qdrant, build indexes, register profiles or migrate. Existing historical reads therefore remain available during a backend outage, subject to rights.
