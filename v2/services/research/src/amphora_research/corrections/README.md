# Research receipt corrections

BP-06.03/B2.02 persistence/API implemented; verified by441 scoped source and334 installed-owner tests.

The private CorrectionPolicy issues immutable chain-bound revisions from this owner's published DomainReceipt. The source adapter must authenticate the actor and load the exact published source from this owner's state; a caller-supplied receipt is not authoritative. Chain scope/issuer, purpose, subject and accepted output scope must match. Superseded notices cannot be sources. Exact deterministic inputs replay identical bytes; each correction preserves the source verdict/output and records actor, reason and predecessor hash. Root revisions are chain-bound too. A new notice names the old effective revision and replacement, without mutating the original receipt.

CorrectionRevision owns stable record hashing. DTOs only serialize state. No peer SQL, network calls, Runtime mutation or shared owner policy. Active campaign pins remain valid under the future-campaign-only policy. Insufficient evidence remains insufficient; an exploratory workflow may use declared alternatives rather than treating an abstention as acceptance.

CorrectionStore provides exact change identity replay/conflict, scoped actor binding, trusted predecessor reconstruction, head comparison and atomic record/notice publication. It loads only this owner's immutable published assessment receipt before opening the write transaction. No peer calls. Exact committed replay bypasses source reselection. The head is the highest committed ordinal, read through the primary-key index; no separately mutable head can diverge. Scoped change and chain advisory transaction locks serialize retries and competing successors. An exact expected predecessor is required; stale heads conflict. research_0005 adds one append-only table with SELECT/INSERT service grants; no earlier migration changes. Requests and records are each bounded at2MiB. Ordinary owner HTTP bodies remain16KiB. Tests live under this service's tests/corrections directory. Owning plan: BP-06.03 Receipt correction implementation.

Correction and selection routes require distinct scoped grants. Selection can explicitly request the latest head or an exact record hash/ordinal, and returns the entire record with original source receipt and effective receipt. It never repins a running campaign. Authenticated read authority covers the scoped chain, while mutation also enforces the original assessment actor. Startup checks the migrated table; it does not migrate. A clean rebuild must preserve these identities, hashes, ordered lock behavior, append-only grants and truthful HTTP dispositions; tests/corrections covers competing writers, rollback, exact history, source-only authority and API grants. Actual public correction transitions and live Runtime original-pin/receipt acceptance are verified in B2.04/B3.01. Additional delivery faults and child closeout remain B3.03/V1.
