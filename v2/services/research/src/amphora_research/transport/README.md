## Optional assessment and publication API

Research0.10.0 composes the private assessment policy/resolver/store and publication journal/workflow through AssessmentOperations. Research contracts0.5.0 add publication request/status shapes; four additive schemas preserve296 predecessors across wire versions1..4. Graph Runtime/Artifacts are public contract dependencies; no Knowledge implementation or contracts dependency cycle is introduced.

POST /v1/assessments accepts EvidenceAssessmentRequest under assess; POST /v1/assessments/read accepts the same exact request under read_assessment. POST /v1/assessment-publications accepts AssessmentPublicationRequest (scope and assessment_id) under publish_assessment; /v1/assessment-publications/read requires read_assessment_publication. Identity/declaration grants imply none of these actions. All endpoints check authenticated scope and original actor before owner reads/effects. A different request for the same identity conflicts409. Missing records/profiles return404; denied inputs/actors403; invalid immutable evidence422; unavailable peer/protocol503. Resolution errors leave the original intent pending without exposing a false or sufficient result. Retry reconciles that intent; corrected references require a new identity. Terminal assessment replay/read does not need an active profile or peer reevaluation.

Assessment request bodies are bounded256KiB; publication selections16KiB. Existing identity routes keep16KiB. All retain5-second body deadlines, strict duplicate/nonfinite/extra-field rejection and non-cacheable success/history responses. Pure publication selection cannot supply a receipt, payload, publisher, actor or issuer. Publication output returns the exact derivation and fixed synthetic-sufficiency receipt, or pending/failed with possible external effects. Historical publication reads use a read-only lookup; they neither create publication intent nor acquire a lease. A new submit may drive pending publication using stable identities. No background scan or Runtime delivery is implied.

The optional assessment config contains1..32 complete reviewed profiles, a loopback Data endpoint/read-token environment reference, and publisher actor/issuer/publication-token reference. Duplicate scoped profile id/version pairs are rejected even if digests differ. No user request can add profiles/trusted issuers. Configuration remains bounded64KiB by the CLI. Serving verifies Research-owned assessment/publication tables exist; startup never migrates. See ../../../config.assessment.example.json for environment-reference-only configuration with synthetic placeholder artifacts that must be established before use. Data must independently authorize source reads/publication and register the assessment payload schema from the publication module. Default configuration remains identity-only; optional routes are absent without configuration. Health/check truthfully reports synthetic_assessment when enabled, not scientific readiness.

Tests remain under tests/api plus actual peer orchestration in tests/assessment/test_actual_resolution.py. The actual process proof submits/evaluates/publishes through Research HTTP, rejects a wrong credential, replaces the Research process and replays history, including with Data offline. Scripted resolver API tests isolate permission, malformed-input and failure mappings; they do not substitute for actual producer resolution. Source-process coverage excludes executed code inside subprocesses. ## Future-campaign receipt correction API

With the assessment profile enabled, POST /v1/assessment-receipts/correct takes CorrectAssessmentReceipt under correct_assessment_receipt. POST /v1/assessment-receipts/select takes SelectAssessmentReceipt under select_assessment_receipt. Each requires the exact authenticated scope; mutation also preserves original assessment actor authority. Neither grant implies assess/publish or the other grant. These operations use private correction storage only and make no peer calls. The caller identifies an already-published owner assessment, never supplies a verdict. Responses are ReceiptCorrectionView, including the exact reusable reference and correction record; explicit selection requests latest (revision null) or a pinned record reference. Mutation uses expected_head null for create and exact predecessor for append. Identity/head conflict and unpublished source return409, scope/actor denial403, absent selection404. JSON/body bounds and no-store behavior match existing16KiB selection routes. See the correction module README for transaction and replacement invariants. Runtime pins remain unchanged.
