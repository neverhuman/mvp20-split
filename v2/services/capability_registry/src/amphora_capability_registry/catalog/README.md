# Registry Application Boundary

`Registry` owns authenticated scoped register/read/lifecycle/deployment/heartbeat/resolve behavior. It calls only its private PostgreSQL owner and public contract packages. It performs no tool dispatch, runtime admission, peer SQL, provider I/O or scientific promotion. `Principal` owns actor/scope/action checks; `ReleaseRecord` verifies stored canonical bytes/locks; `Lifecycle` owns explicit revisioned transitions; `ReceiptFactory` maps outcomes.

Registration stores a structurally valid immutable descriptor under scoped capability/release/contract identity and starts at `registered`. Re-registering identical bytes returns the current projection without rewriting history; changed bytes conflict. Release identity length is bounded to the private key width. Activation is an explicit permission and permits only the initial synthetic/pure profile. Allowed transitions are registered→active, active→draining and registered/active/draining→revoked. No transition revives revoked/draining releases. Existing campaign pins never change.

Deployments pin an exact release, architecture/OS and allowed worker identities. Their definition is immutable; lifecycle is revisioned separately. Heartbeats authenticate the declared worker, pin replica ownership, require expected replica revision and bounded free slots, and use the database clock after locking. TTL is 1–60 seconds. Each release permits at most 64 retained deployment identities; each deployment permits at most 64 retained replica identities. These finite initial limits are not an unbounded fleet/retirement claim.

Resolution requires the full exact LockEntry, typed input/output need and scientific context. Only active releases/deployments with unexpired heartbeats matching the configured host profile contribute capacity. Structural/scientific/permission/resource observations remain distinct. A candidate is an expiring observation, not a capacity reservation, execution grant or selected runtime worker. Runtime alone owns claim/fence/revocation/acceptance. Remote host profiles, routing consumers and runtime replacement integration are later gates.

Every valid authorized command stores its original terminal receipt and audit event atomically with owner changes. Replaying a resolve command returns its original time-bounded observation, even when expired; issue a new command identity to obtain a fresh decision. Replaying a registration or heartbeat likewise cannot rewrite history or extend a lease. Authority is checked before replay. Parse/authentication failures have no command record; deterministic domain rejections are recorded after rolling back partial work. Unexpected failures roll back the entire transaction.

HTTP operations: `POST /v1/registry/{register|activate|drain|revoke|deploy|drain_deployment|revoke_deployment|heartbeat|resolve}`, `GET /v1/releases/{descriptor_sha256}`, `GET /v1/deployments/{deployment_id}`. Reads use the authenticated scope. Commands use public `CommandIdentity` and a family-specific payload; payloads never confer grants. POST returns a typed accepted/rejected RegistryReceipt; parse errors are 422, authentication 401, forbidden 403, inaccessible reads 404, changed command identity 409. Bodies are bounded to the canonical 256 KiB profile. The ASGI factory takes explicit registry/credential objects; the independent Host/CLI supplies validated configuration and own-role readiness.

Tests live under `tests/persistence/` and `tests/api/`; select registry/persistence or registry/api. Descriptor tests remain independently selectable. Current boundary tests cover real PostgreSQL replay/rollback and role denials plus authenticated ASGI flows. B2 proves deeper lifecycle/capacity policy cases; B3 proves real-process races and cross-version routing; V1 proves installed hosting and retained-state replacement. Do not treat TestClient as independent-process evidence.

`ReplicaIdentity`, `ReplicaLease` and `ReplicaPolicy` now own replica observation behavior and its wire projection. B2 verification: 114 registry cases, 96% expanded owner line/branch coverage (711 statements/202 branches); actual process races and installed state replacement are separately measured B3/V1 evidence. Expiry uses real PostgreSQL time, and duplicate heartbeat replay preserves the original expiry.

Discovery uses `GET /v1/releases` with optional exact capability_id/release, limit 1?100 and an after-digest cursor. This fixes the closeout gap where callers needed a digest before they could discover a lock. Every query binds authenticated scope; ordering keys are immutable. It is a current inventory view: concurrent insertion before a cursor may appear only on a fresh scan, and lifecycle may change between pages. Inactive/revoked entries remain inspectable; discovery grants no eligibility. Exact resolution still rechecks current lifecycle/capacity and cannot silently substitute another version.
