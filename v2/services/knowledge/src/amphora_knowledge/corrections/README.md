# Knowledge receipt corrections

BP-06.03/B2.03 store/API implemented; 393 broad source plus4 added cases,15 final scoped and186 installed tests pass.

The private CorrectionPolicy issues immutable chain-bound revisions from this owner's published DomainReceipt. The source adapter must authenticate the actor and load the exact published source from this owner's state; a caller-supplied receipt is not authoritative. Chain scope/issuer, purpose, subject and accepted output scope must match. Superseded notices cannot be sources. Exact deterministic inputs replay identical bytes; each correction preserves the source verdict/output and records actor, reason and predecessor hash. Root revisions are chain-bound too. A new notice names the old effective revision and replacement, without mutating the original receipt.

CorrectionRevision owns stable record hashing. DTOs only serialize state. No peer SQL, network calls, Runtime mutation or shared owner policy. Active campaign pins remain valid under the future-campaign-only policy. Insufficient evidence remains insufficient; an exploratory workflow may use declared alternatives rather than treating an abstention as acceptance.

CorrectionStore owns immutable correction history in knowledge.receipt_corrections (knowledge_0007, SELECT/INSERT service grants only). Scope/issuer/change identity and exact actor-bound request bytes govern replay. Scoped change/chain advisory transaction locks serialize retries and expected-head comparison; the highest committed ordinal is the head, so no separate mutable head can diverge. A failed transaction leaves no record or new head. Requests/records are each bounded at2MiB; the existing Knowledge HTTP request limit is256KiB. Tests live under this service's tests/corrections directory. Owning plan: BP-06.03 Receipt correction implementation.

PublicationRequestDocument.for_correction checks the distinct correct_reasoning_receipt grant against the exact source graph scope. PublicationTerminals.read_for_correction restores existing terminal history with original actor, publication request, reasoning identity and policy checks, without inventing publish_reasoning/read_graph grants or peer effects. Missing or unpublished sources cannot create a correction. CorrectionBoundary.read requires select_reasoning_receipt; neither grant implies the other. Selection returns ReceiptCorrectionView containing an exact revision reference plus record, for latest or explicit historical selection.

POST /v1/reasoning-receipts/correct and /select exist only with the publication profile. A rebuild must preserve hashes/identities, source authority, ordered locks, immutable grants, atomic commit and original publication history. Tests/corrections own policy/store/API checks. Publication fixtures use a synthetic protocol peer with real owner PostgreSQL; actual remote correction integration remains B2.04/B3. No Runtime mutation, cross-owner SQL or scientific promotion.
