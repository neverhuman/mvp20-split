# Knowledge HTTP and host boundary

BP-06.02/B1 implementation. Design: [authoring](../../../../../docs/Architecture/Knowledge/Authoring.md). This module composes private Knowledge behavior and public Data/Research clients; it owns no peer state or scientific authority.

The explicit host serves on `127.0.0.1` using FastAPI/Uvicorn, with at most16 concurrent connections. Run `python -m amphora_knowledge check --config <file>` or `serve --config <file> --port 8085`. Importing packages creates no connections. Startup requires the previously migrated `knowledge_service` role, verifies owner-table access and does not migrate or probe peers. Operators apply migrations separately with `knowledge_migrator`.

Configuration is bounded strict JSON (512 KiB), with exact keys `database_url_env`, `principals`, `vocabulary`, `policy`, `data`, `research`, plus optional `reasoning` (at most32 ReasoningRuleSet records) and `publication`. Principals contain `token_env`, `actor_id`, `scope`, `actions`; grants are nonempty subsets of `read_graph`/`propose_graph`/`rebuild_graph`/`reason_graph`/`publish_reasoning`. Tokens and database URLs are environment references, never inline configuration values. Data/Research entries contain `endpoint` and `token_env`; each is an explicit loopback HTTP endpoint. Data credentials need `read` and `source_history`; Research credentials need `read_declarations`. Each peer's scoped credential must match the submitted graph's tenant/project. Incorrect configuration cannot grant cross-owner authority.

`vocabulary` is a public DomainVocabulary; `policy` is the exact definition from StructuralPolicy.definition(), with synthetic structural authority and explicit history caps. Defaults apply only when first intent pins a new graph profile. Existing profiles are immutable; changing process configuration does not migrate them. Profile discovery before first intent is an observation, not a reservation.

| Method/path | Request | Result/authority |
|---|---|---|
| GET /health | none | Static owner/structural authority; no peer readiness claim |
| POST /v1/graph-proposals | GraphChangeProposal | Durable GraphChangeDecision; actor bound to authenticated principal |
| GET /v1/graphs/{graph_id}/proposals/{change_id} | Path identifiers; credential scope | GraphProposalStatus; null decision means pending |
| POST /v1/graph-profiles/read | DomainGraphRef | GraphAuthoringProfile; configured_default or stored |
| POST /v1/graph-heads/read | DomainGraphRef | Exact DomainHead |
| POST /v1/graph-snapshots/read | DomainRevisionRef | Exact immutable DomainGraphSnapshot |
| POST /v1/graph-changes/read | AcceptedChangeRef | Exact immutable AcceptedGraphChange |

All graph routes require bearer authentication and scoped grants. Request parsing has a 256 KiB/5-second bound and rejects duplicate keys, nonfinite JSON, extra fields and caller-injected actor/validation authority. Responses use no-store. Proposal responses return200 for completed accepted/rejected/conflict decisions; clients must inspect the outcome. Changed same-ID content returns409. Unknown exact records return404; scope/action denial403; missing/invalid credentials401; malformed requests422; body limit413; body deadline408; wrong media415. Peer outage/protocol ambiguity returns503 with pending intent; SQL failure returns503 and clients reconcile before retry. A dropped HTTP connection is not evidence that an in-flight transaction was cancelled.

The accepted change links to its base head; clients can traverse immutable prior revisions using exact read requests rather than relying on a mutable offset listing. Profile reads compute the canonical vocabulary hash and return the graph's pinned policy reference. Snapshot/change reads verify stored hashes/identity before returning success. No generic query, private SQL interface or graph mutation by GET exists.

Tests live in `tests/api`: real PostgreSQL plus in-process ASGI verifies credentials/scope, profile pinning, proposal/receipt replay, immutable reads, malformed inputs and pending recovery using scripted peers. Host configuration tests include a separate process `check`. The separate tests/acceptance suite proves actual three-owner HTTP, Knowledge process restart, Research outage/recovery and current-rights rejection. Mid-build interruption is verified through test-only barriers; independent installed replacement accepted (169 initial / 39 replacement tests). Do not infer those proofs from TestClient.

Pending has null result; published/deferred/failed are terminal. A graph without an accepted head returns409; unknown rebuild status returns404. Startup requires knowledge_0002. BP-06.03 adds optional POST /v1/graph-reasoning and GET /v1/graphs/{graph_id}/reasoning/{request_id}; submit requires reason_graph, status read_graph. ReasoningStatus distinguishes null pending, evaluated (possibly incomplete/unknown) and terminal failed decisions. Enabled hosts require knowledge_0003; omission of reasoning omits the routes, an empty list permits existing-request reconciliation. Host configuration caps512KiB even though persisted individual rule profiles cap2MiB. Clients cannot supply rules/actor/validation authority. See [reasoning boundary](../reasoning/README.md). Actual three-owner tests prove current provenance, restart, outage recovery and revoked-source rejection. Optional artifact publication is now implemented below; Runtime receipt delivery remains pending.

Knowledge0.13.0 optional publication configuration has exactly actor_id, issuer_id and token_env, using the existing Data endpoint with an explicit write credential (upload/read/finalize). Data source reads still use the separate configured reader credential. The Data host must install the public reasoning_artifact_schema_document/profile in trusted configuration. Tokens remain environment references. Startup requires knowledge_0006 only when publication is enabled; it never contacts peers. Publication can replay stored reasoning without enabling new reasoning profiles.

Both require publish_reasoning and exact original actor/scope. Unknown status404; disabled feature routes404; authority injection422; failed/published/pending are explicit body outcomes. HTTP200 published does not mean scientifically accepted. SDK protocol/transport ambiguity maps503 and callers reconcile the same identity. ## Future-campaign receipt corrections

The publication-enabled profile adds POST /v1/reasoning-receipts/correct (CorrectReasoningReceipt, correct_reasoning_receipt grant) and /v1/reasoning-receipts/select (SelectReasoningReceipt, select_reasoning_receipt grant). Return ReceiptCorrectionView with exact reference and record. Correction source is an existing owner publication request; no caller verdict or fabricated publication grant. Scoped actor/publication checks remain intact. Selection is explicit latest or exact revision; no active-run repinning. Body/deadline, error and no-store behavior use the existing bounded invocation adapter. See the correction README for storage and replacement invariants.

Knowledge0.17 exposes four read_graph POST routes: `/v1/graph-explore/catalog` (DomainRevisionRef), `/entities` (GraphEntitySearchRequest), `/neighborhood` (GraphNeighborhoodRequest), `/object` (GraphObjectRequest), all under `/v1/graph-explore`. ExplorationBoundary checks the immutable ledger on every call; no implicit latest head, source fetch, new state or grant. Responses carry no-store and are bounded to1MiB. Snapshot corruption returns safe503, absent snapshot404, denied scope/grant403, mismatched query/member409.
