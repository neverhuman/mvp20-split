# Knowledge rebuild publication

BP-06.02/B2 owns reconstruction from accepted history and atomic publication of a replacement materialization. Design: [rebuild protocol](../../../../../docs/Build%20Plans/BP-06/Completed/BP-06.02%20Rebuild%20publication%20design.md). This module neither creates accepted edits nor changes a campaign's pinned semantic revision.

`RebuildRequest.authorized` binds a scoped rebuild ID to the authenticated actor and rebuild_graph grant. First registration captures the complete current head under the graph lock; unknown graphs fail without inventing history. Immutable request bytes encode graph and rebuild_id with sorted compact JSON; actor binding is separate. Same-ID/same-actor retries reconcile the original status; another actor conflicts. `RebuildStatus` is a domain projection; `boundary.py` maps it to public GraphRebuildStatus, with null result for pending and distinct published/deferred/failed terminal outcomes. Public callers cannot submit a snapshot, accepted records, policy or actor authority.

`RebuildHistory` reads the stored graph profile and bounded immutable accepted-log slices. SQL connections close before replay. ReplayCursor verifies the exact prefix through the initially captured head, then only the accepted tail for each catch-up round. Each round creates an immutable Candidate with complete canonical snapshot bytes and exact semantic head. Three publication attempts are allowed per execution; continuous edits produce a durable deferred result. Interrupted pending requests may retry from the original watermark, so three is not a lifetime audit-row cap across all retries.

`RebuildStore.stage` commits private candidates. `publish` takes the same graph-scoped transaction lock as incremental acceptance, checks the full current head and candidate binding, then atomically switches the publication pointer and stores a terminal published result. A stale head returns no publication, allowing bounded catch-up. Terminal results are immutable; concurrent duplicate requests return the first committed result even if both created private candidates. Failed/deferred outcomes never switch the pointer. Exceptions before transaction commit leave the old complete snapshot readable and the intent pending.

Migration knowledge_0002 adds rebuild_intents, rebuild_candidates, rebuild_results and snapshot_publications. It does not modify knowledge_0001 or rewrite accepted canonical records. Composite foreign keys bind candidates to accepted heads and publication pointers to a published result; the latter is deferred until transaction commit. Histories allow service SELECT/INSERT only; only publication-pointer columns allow UPDATE. Candidate bytes are capped at16 MiB; slices at10000 records/64 MiB. A graph's existing history-admission limits bound total replay. No graph/session lock or reserved database connection spans CPU replay or peer I/O.

KnowledgeLedger.snapshot selects a published candidate only for the exact requested semantic reference, otherwise the original immutable snapshot. Both paths verify graph/revision/content hash. Advancing the semantic head does not erase an older materialization: newer reads fall back to the new accepted snapshot until a matching rebuild publishes. Historical refs remain stable. This is a physical projection replacement, not scientific reacceptance or a source-rights renewal. Rebuild never rereads Data payloads or re-prompts prose.

Public routes: POST /v1/graph-rebuilds takes GraphRebuildRequest and requires rebuild_graph; POST /v1/graph-rebuilds/read takes the same identity and requires read_graph. Both return GraphRebuildStatus. Unknown status returns404; a graph with no accepted head cannot start rebuilding. Request parsing/authentication and failure codes follow the sibling transport README. A dropped connection does not mean an in-flight publication was cancelled; reconcile the original identity.

Tests live in tests/rebuild, with API mapping in tests/api and actual owner hosting in tests/acceptance. PostgreSQL tests cover stale-CAS catch-up, contention deferral, duplicate builders, rollback after pointer write, private staged candidates, damaged replay, scope/actor grants, deferred foreign keys and immutable history permissions. B3 verifies actual process death during rebuild, correction/publication races and named QEV/TRACE lineage cases; independent installed replacement accepted (169 initial / 39 replacement tests). No power-loss durability or scientific-validity claim follows from these software tests.
